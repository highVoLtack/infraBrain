# Phase 12.6: Self-Healing Executor - Research

**Researched:** 2026-03-14
**Domain:** Execution engine self-correction loop, error-driven LLM retry
**Confidence:** HIGH

## Summary

The self-healing executor replaces the brittle `fixKnownCommandErrors()` regex sanitizer in `planner.ts` with an error-driven correction loop inside the executor. When a command fails, the executor captures stderr + exit code, sends them to an LLM with the original command and step context, and retries with the corrected command -- exactly how a human would read `--help` after getting syntax wrong. This approach is fundamentally more robust because it handles ANY error variant, not just the 4 patterns the regex knows about.

The current architecture has clear integration points. The executor (`executor.ts`) runs a step loop that delegates to `CircuitBreaker` for retries. The circuit breaker currently does blind retries of the SAME command -- it needs to become LLM-corrected retries of DIFFERENT commands. The correction pipeline must go through the full safety stack: `enforceSkillAllowlist()` + `validateCommand()` + `dynamicRewrite()`. The `DamageBudget` already tracks retry costs (`deductFailedRetry`), which naturally extends to correction costs.

**Primary recommendation:** Build a `SelfHealingExecutor` module that wraps the existing runner, intercepts failures, calls the LLM for correction, validates the corrected command through the full safety pipeline, and retries. Replace `CircuitBreaker`'s blind retry logic with this LLM-corrected retry. Remove `fixKnownCommandErrors()` entirely. Cap at 3 correction attempts per step with damage budget tracking per attempt.

### Pattern 1: Error-Driven Correction Loop
**What:** When a command fails, build a correction prompt with error context, call LLM, validate corrected command through safety pipeline, retry.
**When to use:** Every command failure in the executor step loop.
**Example:**
```typescript
// In executor.ts, replacing the current CircuitBreaker blind retry:

interface CorrectionAttempt {
  originalCommand: string;
  correctedCommand: string;
  error: { stderr: string; exitCode: number };
  outcome: 'success' | 'failed' | 'blocked_by_safety';
}

interface SelfHealResult {
  status: 'success' | 'exhausted' | 'budget_exceeded';
  finalResult?: RunResult;
  attempts: CorrectionAttempt[];
  commandUsed: string; // The command that actually succeeded (or last tried)
}

async function selfHealStep(
  step: FixStep,
  failedResult: RunResult,
  context: SelfHealContext,
): Promise<SelfHealResult> {
  const attempts: CorrectionAttempt[] = [];

  for (let i = 0; i < context.maxAttempts; i++) {
    // 1. Check damage budget
    if (!context.budget.canAfford(context.budget.costFor(step.risk))) {
      return { status: 'budget_exceeded', attempts, commandUsed: step.command };
    }

    // 2. Build correction prompt (fresh each time -- no previous attempts)
    const prompt = buildCorrectionPrompt({
      originalCommand: step.command,
      stderr: failedResult.stderr,
      exitCode: failedResult.exitCode,
      stepDescription: step.description,
      availableTools: context.toolList,
      containerContext: context.containerInfo,
    });

    // 3. Call LLM for correction
    const correctedCommand = await generateCorrectedCommand(prompt, context.model);

    // 4. Validate through FULL safety pipeline
    //    allowlist -> validator -> dynamic rewriter
    const safetyResult = validateCorrectedCommand(correctedCommand, context);
    if (!safetyResult.allowed) {
      attempts.push({
        originalCommand: step.command,
        correctedCommand,
        error: { stderr: failedResult.stderr, exitCode: failedResult.exitCode },
        outcome: 'blocked_by_safety',
      });
      context.budget.deductFailedRetry(step.risk);
      continue;
    }

    // 5. Execute corrected command
    const result = await context.runner.run(safetyResult.command, ...);
    context.budget.deduct(context.budget.costFor(step.risk));

    if (result.exitCode === 0) {
      attempts.push({
        originalCommand: step.command,
        correctedCommand: safetyResult.command,
        error: { stderr: failedResult.stderr, exitCode: failedResult.exitCode },
        outcome: 'success',
      });
      return { status: 'success', finalResult: result, attempts, commandUsed: safetyResult.command };
    }

    // 6. Failed again -- update failedResult for next iteration
    failedResult = result;
    attempts.push({
      originalCommand: step.command,
      correctedCommand: safetyResult.command,
      error: { stderr: result.stderr, exitCode: result.exitCode },
      outcome: 'failed',
    });
  }

  return { status: 'exhausted', attempts, commandUsed: step.command };
}
```

### Pattern 2: Correction Prompt Builder
**What:** Build a focused prompt for the LLM that includes error context, step goal, and available tools.
**When to use:** Every correction attempt.
**Example:**
```typescript
function buildCorrectionPrompt(ctx: {
  originalCommand: string;
  stderr: string;
  exitCode: number;
  stepDescription: string;
  availableTools: string;
  containerContext: string;
}): string {
  return `The following command failed during execution:

Command: ${ctx.originalCommand}
Exit code: ${ctx.exitCode}
Error output:
${ctx.stderr}

This command was part of a fix plan step: "${ctx.stepDescription}"
${ctx.containerContext}

${ctx.availableTools}

Generate a corrected command that achieves the same goal.
Output ONLY the corrected command, nothing else.`;
}
```

### Pattern 3: Safety Pipeline for Corrected Commands
**What:** Every corrected command passes through the same validation as original commands.
**When to use:** After LLM generates a corrected command, before execution.
**Example:**
```typescript
function validateCorrectedCommand(
  command: string,
  context: SelfHealContext,
): { allowed: boolean; command: string; reason?: string } {
  // 1. Per-skill allowlist
  const allowlistResult = enforceSkillAllowlist(command, context.skill);
  if (!allowlistResult.allowed) {
    return { allowed: false, command, reason: allowlistResult.reason };
  }

  // 2. Global safety validator (includes sanitizeDockerExec)
  const validationResult = validateCommand(command, context.safetyConfig);
  if (!validationResult.allowed) {
    return { allowed: false, command, reason: validationResult.reason };
  }

  // 3. Dynamic rewriter (docker exec wrapping, user injection, etc.)
  const rewritten = dynamicRewrite(
    validationResult.command,
    context.rewriteRules,
    context.containers,
  );

  return { allowed: true, command: rewritten };
}
```

### Anti-Patterns to Avoid
- **Including previous correction attempts in prompt:** The CONTEXT.md explicitly says "Do NOT include previous correction attempts (avoid confusion spiral)." Each attempt must be fresh with just the latest error.
- **Using circuit breaker for blind retries alongside self-healing:** The self-healing loop IS the retry mechanism. Don't run both.
- **Trusting exit code 0 alone after correction:** Per user decision, verify actual effect after self-healed success. A command might exit 0 but not actually achieve its goal.
- **Hardcoding container names or paths in correction prompt:** Use discovery data and skill context, not hardcoded values.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Command validation | Custom validation for corrected commands | `enforceSkillAllowlist()` + `validateCommand()` + `dynamicRewrite()` | These already handle all edge cases (TTY stripping, blocklist, allowlist, docker exec rewriting) |
| LLM text generation | Custom HTTP calls to Ollama | `generateText()` from Vercel AI SDK via `LLMProvider` | Already abstracts model selection, token budgets, retry logic |

| Damage budget tracking | Separate correction budget | Existing `DamageBudget` class with `deductFailedRetry()` | Already has the exact cost model needed |

**Key insight:** The self-healing loop is primarily an orchestration concern -- connecting existing pieces (LLM calls, safety validation, damage budget) in a new error-driven flow. Almost all building blocks exist. The only new code is the correction prompt builder and the orchestration loop itself.

## Common Pitfalls

### Pitfall 1: Confusion Spiral from Correction History
**What goes wrong:** Including all previous correction attempts in the prompt causes the LLM to get confused and repeat the same mistakes.
**Why it happens:** LLMs treat context as authoritative. Showing them 3 wrong commands teaches them to generate similar wrong commands.
**How to avoid:** Each correction attempt is FRESH. Include only: original command, latest error, step description, available tools. Per CONTEXT.md decision.
**Warning signs:** Corrected commands look similar to previous failed corrections.

### Pitfall 2: LLM Returns Non-Command Output
**What goes wrong:** The LLM returns explanatory text, markdown formatting, or multiple commands instead of a single corrected command.
**Why it happens:** Local 7B models are bad at "output ONLY the corrected command" instructions.
**How to avoid:** Parse the LLM response aggressively: strip markdown code fences, take only the first non-empty line, trim whitespace. If the response looks like prose (contains multiple sentences without command-like patterns), reject the attempt.
**Warning signs:** Corrected "command" contains newlines, starts with "The", or has markdown formatting.

### Pitfall 3: Infinite Cost Escalation
**What goes wrong:** Each correction attempt costs damage budget AND an LLM call. With 5 steps each getting 3 corrections, that's 15 extra LLM calls.
**Why it happens:** Self-healing is expensive by design -- it trades compute for correctness.
**How to avoid:** Hard cap at 3 attempts (user decision). Each attempt costs 1 WRITE point. Budget exhaustion triggers halt. Also consider: if first 2 corrections both produce safety-blocked commands, stop early (LLM doesn't understand the safety constraints).
**Warning signs:** Damage budget depleted mid-plan, multiple steps needing correction.

### Pitfall 4: Safety Pipeline Rejects Valid Corrections
**What goes wrong:** The LLM generates a correct command but the safety pipeline blocks it (not in allowlist, blocked pattern match).
**Why it happens:** The correction LLM doesn't know about InfraBrain's safety rules.
**How to avoid:** Include available tools from the skill in the correction prompt. If a corrected command is blocked by safety, that counts as a failed attempt (not a retry of the same command). Log the safety rejection reason in the audit trail.
**Warning signs:** All 3 correction attempts blocked by safety, none reach execution.

### Pitfall 5: Shell Mode vs ExecFile Mode Mismatch
**What goes wrong:** Original command used `parseCommand()` (execFile mode) but the corrected command contains pipes/redirects that need shell mode, or vice versa.
**Why it happens:** The correction LLM might add shell operators to fix the command.
**How to avoid:** Use `needsShell()` on the corrected command independently. If it returns true, use `runShellCommand()` instead of `runCommand()`. The current executor always uses `parseCommand()` -- the self-healer needs to be smarter.
**Warning signs:** Corrected command with `|` or `&&` fails with "command not found" errors.

### Pitfall 6: Exit Code 0 Doesn't Mean Success
**What goes wrong:** Corrected command exits 0 but didn't actually achieve the goal (e.g., `chown` on wrong file, or command ran but didn't change permissions).
**Why it happens:** Many commands exit 0 even when they don't do what you expect.
**How to avoid:** Per user decision, implement verification after self-healed success. For write/destructive steps, check that the intended change actually happened. This is a stretch goal -- basic self-healing should work without it.
**Warning signs:** Self-healed commands "succeed" but the overall fix plan still fails at verification.

### LLM Call Pattern for Corrections
```typescript
// Use generateText from Vercel AI SDK, same pattern as provider.ts
import { generateText } from 'ai';

async function generateCorrectedCommand(
  prompt: string,
  model: LanguageModel,
): Promise<string> {
  const { text } = await generateText({
    model,
    prompt,
    maxOutputTokens: 512, // Commands are short
  });

  // Aggressively parse: strip fences, take first command-like line
  return extractCommandFromLLMResponse(text);
}

function extractCommandFromLLMResponse(text: string): string {
  let cleaned = text.trim();

  // Strip markdown code fences
  cleaned = cleaned.replace(/^```\w*\n?/, '').replace(/\n?```$/, '');

  // Take first non-empty line that looks like a command
  const lines = cleaned.split('\n').map(l => l.trim()).filter(Boolean);
  for (const line of lines) {
    // Skip lines that look like prose
    if (/^(The|This|I |You |Note|Here|To )/.test(line)) continue;
    // Skip lines that are just punctuation or short explanations
    if (line.length < 3) continue;
    return line;
  }

  // Fallback: return everything
  return cleaned;
}
```

## Open Questions

1. **Which model role for corrections?**
   - What we know: The plan is generated by `strategic` (70B). The worker model is 7B (may be too weak to fix its own errors).
   - What's unclear: Whether the same model that generated the broken command can fix it, or if a different model perspective helps.
   - Recommendation: Use `default` model role for corrections. It's the general-purpose model and corrections are simple tasks (parse error, adjust syntax). Allow configuration override.

2. **Verification after self-healed success**
   - What we know: CONTEXT.md says "verify actual effect" after exit 0.
   - What's unclear: How to generate verification commands automatically. For `chown`, you'd run `ls -la` after. But the executor doesn't know what verification to run.
   - Recommendation: Defer full verification to the existing plan structure. Fix plans already have verification steps. If a self-healed command exits 0, trust it for now. The plan's subsequent verification step will catch failures. Full post-correction verification is a stretch goal.

3. **Integration with debug.ts DPEV flow**
   - What we know: The executor is called from the `/execute` route, not directly from `debug.ts`.
   - What's unclear: Whether the self-healer needs access to discovery context from debug.ts (container names, etc.).
   - Recommendation: Pass discovery context (containers, rewrite rules, skill) through `ExecutionDeps`. The `/execute` route already has access to these from the debug session.
