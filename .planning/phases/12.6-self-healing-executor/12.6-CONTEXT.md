# Phase 12.6: Self-Healing Executor - Context

**Gathered:** 2026-03-14
**Status:** Ready for planning
**Source:** User decision + Superpowers/GSD pattern analysis

<domain>
## Phase Boundary

This phase replaces the brittle regex-based command sanitizer (fixKnownCommandErrors) with a self-healing execution loop. The core insight: instead of anticipating every possible LLM syntax error variant with regex, let the executor be self-correcting. When a command fails, show the LLM the error output and let it fix itself — exactly how a human would read `chown --help` after getting the syntax wrong.

**Delivers:**
- Self-healing retry loop in executor.ts
- Error → LLM correction → retry pipeline
- Removal of fixKnownCommandErrors() band-aid
- Correction audit trail for learning
- Permission Trap live DPEV passing without regex patches

**Does NOT deliver:**
- Persistent learning from corrections (future phase)
- Workflow-protocol skills / skill-chaining redesign (future phase)
- Knowledge Layer (Qdrant/BGE-M3) — separate track

</domain>

<decisions>
## Implementation Decisions

### Architecture: Error-Driven Self-Correction Loop
- When a command fails (non-zero exit code), capture stderr + exit code
- Format as structured prompt: "Your command `X` failed with error: `Y`. Generate a corrected command."
- LLM generates corrected command
- Corrected command goes through FULL safety pipeline (allowlist, validator, rewriter) before execution
- Max 3 self-heal attempts per step (configurable)
- Each attempt costs damage budget points (prevents runaway loops)

### Pattern Source: Superpowers Systematic Debugging
- Phase 1 (Root Cause Investigation) maps to: parse error message completely, don't guess
- Iron Law "No fixes without root cause investigation" maps to: always include full stderr in correction prompt
- Red Flag "one more fix attempt when already tried 2+" maps to: hard cap at 3 attempts
- 3+ failures = architectural problem = STOP (don't keep retrying)

### Pattern Source: GSD Deviation Rules
- Rule 1 (Auto-fix bugs): Self-healing IS auto-fix — executor fixes command syntax automatically
- Rule 3 (Auto-fix blockers): Permission errors, missing flags = blockers the executor resolves
- Rule 4 (STOP at architecture): After 3 failed corrections, halt with full context for human review

### Pattern Source: Superpowers Verification-Before-Completion
- After self-healed command "succeeds" (exit 0), verify actual effect
- Don't trust exit code alone — check that the intended change actually happened
- Evidence gate: run verification command after fix, parse output

### Correction Prompt Design
- Include: original command, full stderr, exit code, what the command was trying to achieve (from fix plan step description)
- Include: available tools from skill (so LLM knows valid commands)
- Include: container context (target container name, user)
- Do NOT include: previous correction attempts (avoid confusion spiral)
- Each correction attempt is fresh: just "here's what failed, fix it"

### Integration with Existing Systems
- Self-healing lives inside executor.ts step loop, between command execution and result processing
- CircuitBreaker retry logic replaced/enhanced — not blind retries of same command, but LLM-corrected retries
- Rolling context updated with correction history (so subsequent steps know what actually ran)
- Damage budget tracks correction costs (each attempt = 1 WRITE point)
- Audit trail: original_command → error → corrected_command → outcome logged per step

### What Gets Removed
- fixKnownCommandErrors() in planner.ts — entire function deleted
- All callers of fixKnownCommandErrors() updated to remove calls
- The 4 regex patterns (TTY strip, -u placement, missing root, shell expansion) no longer needed
- Comments/docs referencing the sanitizer updated

### Claude's Discretion
- Exact prompt template wording for correction LLM call
- Whether to use same model or lightweight model for corrections
- Internal function naming and module structure
- Test strategy details (unit vs integration split)

</decisions>

<specifics>
## Specific Ideas

### The Correction Prompt Template (Inspiration)
```
The following command failed during execution:

Command: {original_command}
Exit code: {exit_code}
Error output:
{stderr}

This command was part of a fix plan step: "{step_description}"
Target container: {container_name}

Available tools for this skill: {tool_list}

Generate a corrected command that achieves the same goal.
Output ONLY the corrected command, nothing else.
```

### Superpowers Patterns to Embed
- "Each fix reveals new problem in different place" = STOP signal (architectural issue)
- "Condition-based verification" — don't sleep-and-retry, check actual state
- "Evidence before claims" — verify fix effect, don't trust exit code

### GSD Patterns to Embed
- Deviation tracking: log what changed from original plan
- Checkpoint on architectural failure: if 3 corrections fail, create detailed halt report
- Goal-backward: verify the GOAL of the step was achieved, not just that a command ran

### User Quote (Design Intent)
"chown --help ist ein Befehl — warum kann man die KI das nicht machen lassen?"
(chown --help is a command — why can't you let the AI do that?)

</specifics>

<deferred>
## Deferred Ideas

- **Persistent correction learning**: Store successful original→corrected pairs in a database, use as few-shot examples for future corrections (v2.0+)
- **Workflow-protocol skills**: Restructure skills as workflow protocols that steer HOW the model thinks, not just WHAT it knows (separate phase)
- **Skill chaining enforcement**: discovery → diagnosis → planning → execution → verification as enforced protocol sequence (separate phase)
- **`<why_this_matters>` sections**: Add output contract documentation to skill frontmatter (separate phase)
- **Command template library**: Pre-validated command templates per tool that LLM selects from instead of generating (alternative approach, deferred)

</deferred>
