# Phase 12.4: Agnostic Skill Redesign - Context

**Gathered:** 2026-03-14
**Status:** Ready for planning
**Source:** User specification + SKILL-REDESIGN-RESEARCH.md

<domain>
## Phase Boundary

This phase fundamentally redesigns how skills work. Instead of scripted Diagnostic Ladders that tell the LLM step-by-step what to run, skills provide Domain Knowledge and let the LLM reason. Instead of three separate systems for tool permissions (tools[], rewrite_rules[], DEFAULT_RULES), one unified tools map. Instead of scenario-specific skills with hardcoded container names, universal expert skills that work for any instance.

The user's test: "I want to rename my Docker containers to anything, and InfraBrain should still fix them because it understands the DOMAIN, not the DEMO."

</domain>

<decisions>
## Implementation Decisions

### Schema: Unified Tool Map
- New `ToolDeclarationSchema`: `{ risk: read|write|destructive, user?: string, wrapper?: string, strip_flags?: string[], container?: string }`
- `tools` field becomes `Record<string, ToolDeclaration>` instead of `string[]`
- Backward compatible via `z.union()` during migration, then cleanup
- `rewrite_rules` field removed from frontmatter — merged into tools

### Engine: toolsToRewriteRules Adapter
- New `toolsToRewriteRules()` in dynamic-rewriter.ts converts tool map → RewriteRule[]
- debug.ts changes ONE line: `toolsToRewriteRules(skill.tools)` instead of `skill.rewrite_rules`
- allowlist.ts uses `Object.keys(skill.tools)` instead of flat array

### Engine: Auto-Generated Tool List
- `context.ts` auto-generates a `## YOUR TOOLS` section from the tool map
- Injected into LLM system prompt alongside MANDATORY_EXECUTION_PROTOCOL
- Lists each tool with risk level and capabilities
- "You MUST NOT use any tool not listed here"

### Skill Content: Universal Experts
- 4 scenario skills → 2-3 universal experts:
  - `linux-expert.md` — replaces linux-filesystem-troubleshoot + docker-storage
  - `postgres-expert.md` — replaces postgres-troubleshoot
  - `network-expert.md` — replaces nginx-troubleshoot
- Domain Knowledge sections replace Diagnostic Ladders
- No hardcoded container names anywhere in prompts/examples
- Generic discovery: `docker ps -a`, `docker stats --no-stream`

### What Stays
- MANDATORY_EXECUTION_PROTOCOL (anti-hallucination)
- checkForHallucinations() sanity checker
- GROUND TRUTH injection from discovery
- BLOCKED_PATTERNS + DEFAULT_RULES as belt-and-suspenders fallback
- dynamicRewrite() internal logic — only the input changes
- Entire execution pipeline (executor, circuit breaker, damage budget)
- planning.md, verification.md, log-analysis.md unchanged

### Claude's Discretion
- Exact Domain Knowledge sections per skill
- Whether nginx needs its own `network-expert` or can fold into `linux-expert`
- E2E test updates for canned fix plans
- Whether to keep old skill files as deprecated or delete them

</decisions>

<specifics>
## Specific Ideas

- The user's skill template:
```yaml
tools:
  ls: { risk: read }
  chown: { risk: write, user: "0" }
  docker: { risk: read }
discovery:
  - command: "docker ps -a"
    label: "Container Inventory"
```

- Domain Knowledge structure:
```markdown
## DOMAIN KNOWLEDGE: PERMISSIONS
- If UID mismatch, use chown
- Prefer chown over chmod 777

## DOMAIN KNOWLEDGE: DISK PRESSURE
- Use truncate -s 0, not rm
- Classify before acting: logs vs state

## EXECUTION PROTOCOL
1. Analyze GROUND TRUTH
2. Gather evidence with tools
3. Correlate findings
4. Propose surgical fix
```

</specifics>
