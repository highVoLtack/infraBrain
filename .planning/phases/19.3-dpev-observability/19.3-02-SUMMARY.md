# Phase 19.3 Plan 02: Backend Observability Contracts Summary

Wired the three data flows that Plans 03–05 will render: granular pipeline activity
(`dpev:substatus`), per-phase token/cost usage (`dpev:usage`), a cumulative session footer
(`dpev:session_summary`), and a `/status` endpoint that finally returns the cache, memory,
context and model sections `StatusOverlay.parseOverlayData` has been reading from thin air.

## What Was Built

**Task 1 — Aggregator + SSE contracts** (`216e746` RED, `dc0aac0` GREEN)

`src/state/session-usage.ts` holds a module-scoped `Map<sessionId, UsageTotals>` and exports
`recordUsage`, `getSessionSummary`, `clearSessionUsage`, `_resetAll`, and the `UsageTotals` type.
`recordUsage` folds one LLM call into the running totals, deriving cost through Plan 01's
`computeCost`. Unknown or unpriced models contribute their tokens but zero cost — the token
count stays truthful while the dollar figure only reflects models we actually have rates for.

`src/ui/types.ts` gained three `SSE_EVENT_NAMES` constants and three `SSEEventMap` payloads:
`dpev:substatus` (`label`, optional `phase`), `dpev:usage` (`phase`, `modelId`, `inputTokens`,
nullable `outputTokens` / `totalTokens` / `costUsd`), and `dpev:session_summary` (`sessionId`,
`totalTokens`, `totalCostUsd`, `potentialSavings: number | null` — always null in v1.3 per D-24).
16 tests.

**Task 2 — Pipeline emissions + session summary** (`71315e6` RED, `a0404a2` GREEN)

`src/orchestrator/pipeline.ts` now emits 8 `dpev:substatus` events covering both the parallel and
the sequential path: `Routing skill…` before `selectSkill`, `Filtering noise (worker)…` before
`filterNoise`, `Searching MemPalace…` before `buildWakeUpContext`,
`Calling <model> (structured object)` before the structured diagnosis call, and
`Generating fix plan…` before `generateFixPlan`. In the parallel path the two labels are emitted
at dispatch time — the tasks run concurrently, so emitting inside `task.execute` would produce a
meaningless ordering.

A new `buildUsagePayload` helper builds the `dpev:usage` payload. `dpev:usage` fires twice: once
after the two diagnosis paths converge (so it is emitted exactly once regardless of mode) and once
after planning completes.

`src/api/routes/stream-debug.ts` intercepts `dpev:usage` inside the existing `onEvent` relay,
folds it into the aggregator, and still forwards the event verbatim. `emitSessionSummary` fires at
all four non-disconnect exit paths — successful verification, execution failure, plan rejection,
and no-actionable-plan — always immediately before the terminal `dpev:complete`. The
pipeline-error catch block deliberately stays silent (the client may already be gone). 17 tests.

**Task 3 — `/status` dashboard sections** (`2af65c2` RED, `5cf9f6d` GREEN)

`EntityStore.listAll()` mirrors `CacheStore.listAll` — all rows including expired ones (unlike
`getActive`), `[]` on any error. `/status` gained four sections, each independently
try/catch-wrapped:

| Section | Contents |
|---------|----------|
| `cache` | `totalEntries`, `hitRate` (Σ success / Σ hits), `avgConfidence` |
| `memory` | `incidentCount`, `entityCount`, `walSize` (human-readable), plus the three D-23 v2.0 nulls |
| `context` | `currentTokens`, `maxTokens` from `config.contextWindow` |
| `models` | role → model id, unwrapping object-form `modelMap` entries |

The response shape matches what `parseOverlayData` (StatusOverlay.tsx lines 63-69) already reads,
so Plan 05 needs no adapter. 19 tests.

## Key Decisions

**`req.on('close')` is not a disconnect signal.** The plan and PATTERNS.md both instructed adding
`clearSessionUsage(sessionId)` to the `close` handler. On `http.IncomingMessage`, `close` fires as
soon as the *request body stream* ends — long before the pipeline finishes — so that cleanup wiped
the totals before `dpev:session_summary` could read them. This was caught by a failing test and is
a real production bug, not a test artifact: every session would have reported `0 tokens · $0.00`.
Cleanup now lives exclusively in the `finally` block, which runs on every exit path including a
genuine client disconnect. The existing approval-map cleanup in `close` is unaffected because it
only resolves *pending* promises, of which there are none at that instant.

**Real input tokens, null cost.** D-11 states that only the output side and the cost fall back to
`–` when the provider stays silent, because we know exactly what prompt we sent. `buildUsagePayload`
counts the actual diagnosis/planner prompt with the existing Qwen3 BPE tokenizer
(`src/context/token-counter.ts`, already warm in this code path via `ContextManager`) and leaves
`outputTokens`, `totalTokens` and `costUsd` null. Cost stays null rather than being computed from
the input side alone — an input-only figure would understate the real cost, which is the same class
of lie Plan 01's `computeCost → null` decision exists to prevent. Token counting is best-effort:
a tokenizer failure degrades to 0 and never throws.

**Emit-at-dispatch for parallel tasks.** In the parallel path the 9B-preprocess and 122B-diagnosis
tasks are handed to the scheduler together. Both substatus labels are emitted just before
`scheduler.runParallel(tasks)` so the UI shows the concurrent work starting, rather than two labels
racing from inside the task bodies.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Plan's expected cumulative cost was arithmetically wrong**

- **Found during:** Task 1 (writing the RED test)
- **Issue:** The plan's `<behavior>` block asserts that recording 1000/500 then 2000/1000 tokens on
  `gemini-2.5-pro` yields `totalCostUsd: 0.0125`. The second call costs
  `2 × 0.00125 + 1 × 0.005 = 0.0075`, so the cumulative total is `0.00375 + 0.0075 = 0.01125`.
- **Fix:** Test asserts `0.01125` via `toBeCloseTo` (floating-point addition is not exact here).
- **Files modified:** `tests/state/session-usage.test.ts`
- **Commit:** `216e746`

**2. [Rule 1 - Bug] `clearSessionUsage` in the disconnect handler destroyed the summary**

- **Found during:** Task 2 (two stream-debug tests reported `totalTokens: 0` after a usage relay)
- **Issue:** As specified, `req.on('close', …)` cleared the aggregator. Node fires that event when
  the request body stream ends — i.e. between the pipeline's usage emission and the summary
  emission — so `dpev:session_summary` always reported zeros.
- **Fix:** Removed the call from the `close` handler with an explanatory comment; the `finally`
  block remains the single cleanup point and covers real disconnects too.
- **Files modified:** `src/api/routes/stream-debug.ts`
- **Commit:** `a0404a2`

**3. [Rule 2 - Missing critical] `inputTokens: 0` placeholder replaced with the D-11 local count**

- **Found during:** Task 2
- **Issue:** The plan's action block emits `inputTokens: 0` with a "wire this later" TODO. That
  renders `in:0` in the UI — indistinguishable from a genuinely empty prompt, and directly contrary
  to D-11 ("we know the prompt we sent, so we can count input tokens locally").
- **Fix:** Added `buildUsagePayload`, which counts the real prompt with the existing
  `countTokens` BPE wrapper and keeps output/total/cost null.
- **Files modified:** `src/orchestrator/pipeline.ts`
- **Commit:** `a0404a2`

**4. [Rule 3 - Blocking] `parallelDiagModelId` was scoped inside an audit try-block**

- **Found during:** Task 2
- **Issue:** The model id needed by both the substatus label and the usage payload was declared
  inside the non-critical audit `try { … }`, so it was unreachable outside it.
- **Fix:** Hoisted the declaration above the try-block; the audit call now reads the outer binding.
- **Files modified:** `src/orchestrator/pipeline.ts`
- **Commit:** `a0404a2`

## Known Stubs

**`/status` → `context.currentTokens` is hardcoded to `0`.** The live per-session token figure is
owned by the streaming state, which Plan 03 builds (`SESSION_SUMMARY` / `USAGE_UPDATE` reducer
actions). Wiring it here would require `/status` to reach into SSE session state that does not yet
exist. `context.maxTokens` is real, so `parseOverlayData` renders a correct `0%` bar rather than a
wrong one. **Resolved by:** Plan 03 (reducer) feeding Plan 05 (overlay), which can compute the
percentage client-side from the session state it already holds.

This is the only stub. Everything else in the plan's `must_haves` is fully wired and exercised.
