# Phase 19.3 Plan 06: Replay Parity + Keyboard Arbitration Summary

The phase-closing plan. It extends `buildReplayState` to the observability shape the live panel now
renders, and — on expanded scope from the 19.3-04 live run — gives the Ink app a single explicit
keyboard owner, closes Plan 05's `sessionTokens` seam, and stops the session footer claiming a cost
it does not know.

## What Was Built

### Task 1 — buildReplayState reconstructs the full step shape (`69c0046` RED, `830a1b6` GREEN)

The step-extraction branch was a push-only loop gated on `meta?.command`, so a `step_complete`
without a command was dropped and a second event for the same step appended a duplicate. It is now a
merge by `stepIndex` that mirrors the runtime `STEP_UPDATE` reducer field-for-field: the later event
owns `status` / `stdout` / `stderr`, and never erases the `command` / `risk` / `target` / `total` an
earlier event captured. Every field is read through a `typeof` guard rather than a cast, so a
malformed audit row degrades to `undefined` instead of putting a non-string into `StepState`.

Two correctness details the plan did not anticipate:

- **`execution_start` is two different events.** `src/execution/executor.ts:86` logs a *plan-level*
  envelope (`{ planSummary, target, stepCount }`) with no `stepIndex`. The plan's snippet defaulted
  `stepIndex` to `executionSteps.length`, which would have materialised that envelope as a phantom
  step with an empty command at index 0. The guard is now `typeof meta.stepIndex !== 'number'` →
  skip. Pinned by its own test.
- **`status: 'pending'`** for `execution_start` means an approved-but-never-run step replays as
  pending rather than silently as `success`.

The return value gained `expandedPhases: {}` (D-04). Plan 04 already wrote
`state.expandedPhases?.[i] ?? (phase.status === 'active')`, so replay renders every phase collapsed
with no change to the panel.

### Task 2 — replay-mode render coverage (`af50ca2`)

Seven cases over the replay branch: collapsed bodies with `expandedPhases: {}`, `MarkdownView` on
expand (asserting the styled heading appears and the raw `# ` token does not), step command + risk
badge + target, stderr on a failed step, the session footer, a full
`buildReplayState` → `render` round trip, and a source-level assertion that the replay branch
registers no `useInput` (the plan's must-have "replay is read-only").

**No production change was required** — this task is coverage over a contract Plan 04 already
shipped, so it is a single `test(...)` commit rather than a RED/GREEN pair. Recorded here so the
missing GREEN is not read as a skipped gate.

### Item C — the session footer stops asserting `$0.00` (`1f1b03d` RED, `a57c468` GREEN)

`DPEVPanel.tsx:288` rendered `totalCostUsd.toFixed(2)` unconditionally. The live run showed two
phases honestly reading `$–` while the footer claimed `Session: 1044 tokens · $0.00` — a real zero
asserted where the value is unknown, which is the failure mode this phase exists to remove.

`totalCostUsd` is a plain `number` on the wire and cannot distinguish "summed to zero" from "nothing
to sum". The phases can:

```typescript
export function formatSessionCost(totalCostUsd: number, phases: DPEVPhaseState[]): string {
  if (totalCostUsd > 0) return `$${totalCostUsd.toFixed(2)}`;
  const anyPricedPhase = phases.some(p => p.usage?.costUsd !== null && p.usage?.costUsd !== undefined);
  return anyPricedPhase ? `$${totalCostUsd.toFixed(2)}` : `$${EN_DASH}`;
}
```

This deliberately resolves the open question the deferred-items entry left ("needs a decision on how
`session-usage.ts` distinguishes summed-to-zero from nothing-to-sum") **without touching
`session-usage.ts`**: the distinction is already recoverable on the client from the per-phase usage
the footer is contradicting. A local model genuinely priced at `$0` still renders `$0.00` — covered
by its own test, because collapsing that case into the en-dash would trade one dishonest render for
another.

`Saved via Memory: $0.00 (v2.0)` was left alone: it is an explicitly labelled v2.0 placeholder about
a feature that does not exist, not a claim about this session's spend.

### Item A — one keyboard owner (`a19d263` RED, `e0d2253` GREEN, `c56e331` fix)

Ink fires **every** registered `useInput` handler per keystroke. `CommandInput` was the only input
consumer in the app without an ownership gate — `SessionPanel`, `EntityPanel` and the entity overlay
all already received `activeFocus` — so it stayed live through sessions and approval gates and
`App.tsx:204` swallowed every printable character. All three reported symptoms are that one fact.

```typescript
export function resolveKeyboardOwner(ctx: KeyboardContext): KeyboardOwner {
  if (ctx.showStatusOverlay) return 'status-overlay';
  if (ctx.showEntityOverlay) return 'entity-overlay';
  if (ctx.activePanel === 'left') return 'session-panel';
  if (ctx.activePanel === 'right') return 'entity-panel';
  if (ctx.sessionActive) return 'dpev-panel';
  return 'command-input';
}
```

Every consumer now derives from that single value — `isActive={keyboardOwner === 'command-input'}`,
`activeFocus={keyboardOwner === 'dpev-panel'}`, and so on. The two ad hoc booleans
(`!showStatusOverlay`, `activePanel === 'left' && !showStatusOverlay`) are gone, and a test asserts
they do not come back.

`resolveEscapeAction` composes it for Esc precedence: overlay → replay → *collapse before exit*. The
`collapse-phase` verdict means "App does nothing" — the panel's own handler collapses on that same
keystroke, and exiting too would unmount the panel before the collapse was ever visible. It applies
only while the panel actually owns the keyboard; with focus on the sessions list the panel's handler
is inactive, so deferring to a collapse that will never happen would make Esc a dead key. That
asymmetry has its own test.

Three consequences that needed handling rather than just accepting:

1. **`s` had to move.** With `CommandInput` standing down during a session, its `onShortcut` path no
   longer sees `s`, and the status overlay would have become unreachable exactly when the UAT asks
   for it. `s`/`g` are now also handled in App's global handler.
2. **…but only for one owner.** The first cut routed them whenever `CommandInput` did not own the
   keyboard, which reintroduced the *same class of leak* on the side panels: `SessionPanel:147` and
   `EntityPanel` both have a `/` search mode that accumulates printable characters, so typing `sshd`
   into session search would have toggled the status overlay. Caught by writing the test before
   assuming the first cut was right — see Deviations. The DPEV panel is the only owner with no text
   entry, so it is the only one that can spare a bare letter.
3. **Arrows and Enter stay clean.** Ink normalises non-alphanumeric keys to `input = ''`, which is
   why they never leaked; nothing in this change reads arrows in the global handler, and the live
   19.3-04 run's finding (↑/↓ do not move `▸` while a `[Y/n]` prompt is up) is preserved by
   `isPhaseInputActive`, which is now ANDed with `activeFocus` rather than replaced by it.

`CommandInput`'s empty-state hint reads `Tab to focus the prompt` when it does not own the keyboard,
so "I cannot type" is visibly explained rather than mysterious.

### Item B — Plan 05's `sessionTokens` seam, closed without the lift

**`useDPEV` was not lifted into `App.tsx`.** Investigating the lift the two prior plans deferred:
`LiveDPEVPanel` is mounted `key={activePrompt}`, so today a new `debug` command remounts it and the
reducer resets for free. Lifted into the root, that reset has no mechanism — `DPEVAction` has no
`RESET`, and adding one means editing `src/ui/types.ts` and `src/ui/hooks/useDPEV.ts`, two files in
no plan's scope, to gain a state the root does not otherwise need. `useSSE` would also have to be
taught to sit idle on an empty prompt. That is a Rule 4 architectural change bought for two scalar
facts.

Instead the panel reports those two facts upward:

```typescript
export interface DPEVLiveStatus {
  sessionTokens?: number;   // D-12 cumulative tokens -> StatusOverlay's Context Window bar
  collapsible: boolean;     // canCollapseFocusedPhase -> App's Esc arbitration
}
```

`projectLiveStatus(state)` is pure and tested; `LiveDPEVPanel` fires it from a `useEffect` keyed on
the two **primitives**, and `App`'s setter returns the previous reference when nothing changed. Both
halves matter: reporting the whole `DPEVState` would re-render `HeaderBar`, `SessionPanel` and
`EntityPanel` on every streamed token, which is precisely the render churn TERM-UX07 is about.

`<StatusOverlay sessionTokens={dpevStatus.sessionTokens} />` — the UI half of the seam is closed and
the Context Window bar is live. **The backend half is not:** `/status` → `context.currentTokens` is
still hardcoded `0` in `src/api/routes/status.ts`, which is outside this plan's files. That only
affects the value when no live session is running, since `sessionTokens` overrides it.
