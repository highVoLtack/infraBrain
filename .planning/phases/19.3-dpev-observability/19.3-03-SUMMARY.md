# Phase 19.3 Plan 03: DPEV State Layer + Phase Header Summary

The bridge between Plan 02's backend events and Plan 04's rendering: five new reducer actions,
the D-17 `exec:step` field-propagation fix, and a `DPEVPhaseHeader` that finally has somewhere to
put a substatus label and a reason to color its timer.

## What Was Built

**Task 1 — Types, reducer, and SSE routing** (`2223c68` RED, `edc4fec` GREEN)

`src/ui/types.ts` grew three groups of fields. `DPEVPhaseState` gained `substatus?: string` (D-05)
and a nullable `usage` object (D-09/D-11). `DPEVState` gained `focusedPhaseIndex` (D-03),
`expandedPhases: Record<number, boolean>` (D-01/D-02), and `sessionSummary` (D-12/D-24). The
`DPEVAction` union gained five variants and its `STEP_UPDATE` variant was widened with optional
`command`, `risk`, `target`, `total`.

`src/ui/hooks/useDPEV.ts` implements all five as pure, spread-only reducer cases:

| Action | Behavior |
|--------|----------|
| `SUBSTATUS_UPDATE` | Sets `substatus` on the active phase; a no-op returning the *same object* when `activePhaseIndex` is out of range |
| `PHASE_FOCUS` | Clamps `index` into `[0, phases.length - 1]` — invalid input never throws |
| `PHASE_EXPAND` | Merges `{ [index]: expanded }` into `expandedPhases` |
| `USAGE_UPDATE` | Attaches usage to the last phase matching `action.phase` by name; no-op when nothing matches |
| `SESSION_SUMMARY` | Stores the three totals; deliberately never touches `status` |

`STEP_UPDATE` now populates all four D-17 fields on the new-step branch and, on the existing-step
branch, preserves them across partial updates with `action.X ?? s.X`. `PHASE_COMPLETE` sets
`substatus: undefined` on the completing phase.

`handleSSEEvent` was hoisted from a `useCallback` closure to an exported module-scope function
taking `(event, data, dispatch)`; the hook now wraps it in a thin memoized callback. It routes the
three new `dpev:*` events and passes the full `exec:step` payload through. 17 tests.

**Task 2 — DPEVPhaseHeader** (`9486a9a` RED, `294494f` GREEN)

New exported pure function `timerColor(phaseName, status)`: `gray` when complete, `yellow` for
`execution`, `cyanBright` for everything else. The header takes an optional `substatus` prop that
falls back to `phase.substatus`, and renders `⟁ {label}` on an indented second line *only* while
the phase is active. The active timer is `bold` + colored; the completed timer is dim gray. The
19.2-02 replay-mode `setInterval` gate is byte-identical to before. 11 tests.

## Key Decisions

**`handleSSEEvent` is now exported.** The plan's Task 1 test list asks for four tests that "mock
dispatch, call handler, assert dispatched action shape" — but `handleSSEEvent` lived inside
`useDPEV`'s `useCallback` and was unreachable from tests. The existing `handleSSEEvent mapping`
describe block in `dpev-panel.test.tsx` works around this by re-applying the action the handler
*would* dispatch, which tests the reducer twice and the handler zero times. That workaround is
exactly why D-17 survived: the reducer was never wrong, the routing was. Hoisting the switch to an
exported module-scope function (with the hook delegating to it) makes the fix genuinely regression-
locked. Zero behavior change — `DPEVPanel` is the only consumer of `useDPEV` and its signature is
untouched.

**`USAGE_UPDATE` searches by name, right to left.** Plan 02 emits `dpev:usage` *after* the phase
completes, so `activePhaseIndex` either points elsewhere or is `-1` by the time the event lands.
Matching by name handles that. The right-to-left scan means a retried pipeline that runs
`diagnosis` twice attaches usage to the most recent attempt rather than the stale first one.

**`complete` outranks `execution` in `timerColor`.** D-08 lists both rules without stating
precedence. Checking `complete` first is the reading that matches the decision's intent ("completed
phases fade to dim") — a finished execution phase should not keep shouting in yellow. Locked in by
an explicit test.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `handleSSEEvent` was not reachable from tests**

- **Found during:** Task 1 (writing the RED tests for cases 13–16)
- **Issue:** The plan's action block specifies four tests that call `handleSSEEvent` with a mock
  dispatch, but the function was a closure inside `useDPEV`'s `useCallback` with no export. Tests
  16 (the D-17 regression lock) cannot be written against the reducer alone — the reducer already
  handled the fields correctly *before* this plan; only the handler dropped them.
- **Fix:** Extracted the switch into an exported module-scope
  `handleSSEEvent(event, data, dispatch)`. `useDPEV` keeps a memoized `onSSEEvent` wrapper, so the
  hook's external contract and `useSSE` wiring are unchanged.
- **Files modified:** `src/ui/hooks/useDPEV.ts`
- **Commit:** `edc4fec`

**2. [Rule 2 - Missing critical] `SUBSTATUS_UPDATE` upper-bound guard**

- **Found during:** Task 1
- **Issue:** The plan's snippet guards only `activePhaseIndex < 0`. Every other index-reading case
  in this reducer (`TOKEN`) guards both ends. An `activePhaseIndex` that exceeds `phases.length`
  would silently produce a no-op map today, but is a latent crash if the case ever indexes directly.
- **Fix:** Guard is `activePhaseIndex < 0 || activePhaseIndex >= phases.length`, matching `TOKEN`.
- **Files modified:** `src/ui/hooks/useDPEV.ts`
- **Commit:** `edc4fec`

**Notes for Plan 04:** `usage.outputTokens` / `totalTokens` / `costUsd` are `null` on every payload
the current backend emits — render an em-dash, never `0` or `$0.00`. `sessionSummary` is `undefined`
until the terminal `dpev:session_summary` arrives, so the footer must handle its absence.
`expandedPhases` is `undefined` before the first `PHASE_EXPAND` — read it as
`state.expandedPhases?.[i] ?? false`. `DPEVPhaseHeader` reads `phase.substatus` on its own, so the
panel need not thread the prop.

**Note for Plan 05:** the live context-window figure Plan 02 stubbed as `0` is now available
client-side as `state.sessionSummary?.totalTokens`, to be divided by `/status`'s real
`context.maxTokens`.
