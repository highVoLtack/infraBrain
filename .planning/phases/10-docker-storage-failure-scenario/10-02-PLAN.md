**System Prompt** — 5-step Diagnostic Ladder (Archetype Protocol with storage-tailored rung names):

CRITICAL rules (same pattern as postgres skill):
- NEVER invent container names — use ONLY names from discovery/docker ps
- Execute one command at a time, no pipes or semicolons
- Gather evidence before proposing fixes

**Step 0: Container Discovery (MANDATORY)**
- Commands: `docker ps --format "{{.Names}}"` and `docker network inspect <network>`
- Purpose: Discover container names, mount topology, identify which containers share volumes
- Output: List containers, identify shared volume mounts

**Step 1: Capacity Check**
- Commands: `df -h /shared` inside containers, `docker system df`
- Purpose: Determine if shared volume is full or near capacity
- Output: Usage percentage, total/used/available space

**Step 2: Ownership Analysis**
- Commands: `du -sh /shared/*` inside each container
- Purpose: Break down space usage per file/directory on shared volume
- Output: Per-file size breakdown showing which files consume the most space

**Step 3: Causal Deduplication** (THE KEY STEP — this is what differentiates InfraBrain)
- Purpose: LLM classifies each file/directory by type and risk: log bloat (safe to truncate) vs application state data (critical, handle with care)
- Analysis: Cross-reference file ownership with container purpose. Logger's bloat.log = safe to truncate. Redis dump.rdb = critical state data — do NOT delete.
- Output: "bloat.log (9MB, logger) = LOG BLOAT [safe to truncate]. dump.rdb (0.5MB, redis) = STATE DATA [preserve]."

**Step 4: Risk-Tiered Remediation**
- Purpose: Generate 4-step fix plan with risk-appropriate actions per bloat classification
- Plan structure:
  1. Read: Identify bloat files via du/ls (captures file paths for rolling context)
  2. Write (Y/n): `truncate -s 0 /shared/bloat.log` — preserves inode, zero disruption. Use `truncate` NOT `rm` to avoid ghost file handle leakage.
  3. Write (Y/n): `docker restart storage-redis` — structured restart. Freeing disk alone does NOT fix a crashed service.
  4. Read: Dual verification — `df -h /shared` shows free space AND `redis-cli PING` returns PONG

**Important Rules section** — same "never invent names" and "one command at a time" rules as postgres skill.

**Tools section** — docker, redis-cli, df, du, truncate with brief descriptions.

**Examples section** — One complete example showing the Docker Storage Bloat scenario with all 5 steps and the 4-step fix plan. Use container names storage-logger and storage-redis. Show the Causal Deduplication reasoning explicitly.
