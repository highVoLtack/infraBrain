# Phase 12.1: Dynamic Command Rewriter - Context

**Gathered:** 2026-03-14
**Status:** Ready for planning
**Source:** User discussion after Phase 12 Permission Trap UAT

<domain>
## Phase Boundary

Phase 12 (Permission Trap) revealed that the hardcoded SQL Rewriter in runner.ts doesn't scale. Every new scenario (Postgres needs psql wrapping, filesystem needs -u 0 escalation, future scenarios need their own rewrites) requires new TypeScript code in the engine. This phase replaces that with a universal, data-driven rewriter where skills declare their own rewrite rules.

The LLM writes only the intent (e.g., `chown 1000:1000 /app/data` or `SELECT * FROM pg_stat_activity`). The skill defines how that intent gets rewritten. The engine applies the rules dynamically.

</domain>

<decisions>
## Implementation Decisions

### Architecture
- New `src/execution/dynamic-rewriter.ts` that reads `rewrite_rules` from skill frontmatter
- Rewrite rules are declarative YAML in skill files, not TypeScript code
- Three rewrite capabilities: container wrapping, privilege escalation (`-u 0`), command wrapping (e.g., `psql -U postgres -c "{cmd}"`)
- Container targeting uses `auto` keyword — resolved from discovery ground truth at runtime
- Existing `rewriteForContainer()` and `stripHostFlag()` logic migrated into skill metadata, then deprecated/removed

### Skill Frontmatter Extension
- New `rewrite_rules` array in skill frontmatter
- Each rule has: `match` (regex), `container` (auto or specific name), `user` (optional, e.g., "0" for root), `wrapper` (optional, e.g., `psql -U postgres -c "{cmd}"`), `risk` (read/write/destructive), `strip_flags` (optional, e.g., ["-h", "--host"])
- Zod schema validation for rewrite rules

### Migration Strategy
- Migrate postgres-troubleshoot.md: SQL patterns → `wrapper: 'psql -U postgres -c "{cmd}"'`, `strip_flags: ["-h", "--host"]`
- Migrate linux-filesystem-troubleshoot.md: chown/chmod → `user: "0"`, ls/id/stat → read-only container exec
- Migrate docker-storage.md: truncate/df/du → container exec rules
- All existing E2E tests must continue passing — backwards compatibility is mandatory

### Safety Integration
- Safety validator still runs AFTER rewriting — belt-and-suspenders
- Risk classification from rewrite rules is advisory — safety validator has final say
- Blocked patterns still enforced regardless of rewrite rules

### Claude's Discretion
- Exact Zod schema shape for rewrite rules
- Whether to keep `rewriteForContainer()` as fallback for skills without rewrite_rules or remove entirely
- How to pass active skill context to the rewriter (plumb through executor)
- Test strategy (unit tests for rewriter + existing E2E as integration tests)

</decisions>

<specifics>
## Specific Ideas

- The rewriter should be a pure function: `rewriteCommand(command: string, rules: RewriteRule[], containers: string[]): string`
- Container `auto` resolves to the first container from discovery, or uses `findDbContainer` logic if multiple
- If no rewrite rules match, command passes through unchanged (safe default)
- The `wrapper` pattern uses `{cmd}` as placeholder for the original command
- Strip flags applies before wrapping (e.g., strip `-h` from psql, then wrap)
- nginx-diagnose skill may not need rewrite rules (uses standard docker/nginx commands directly)

</specifics>

<deferred>
## Deferred Ideas

- Per-container rewrite rules (for multi-container scenarios) — v2
- Conditional rewrite rules based on OS detection — v2
- Rewrite rule inheritance (base rules + skill-specific overrides) — v2

</deferred>
