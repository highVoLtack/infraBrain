### Schema Duplication Detail

Two definitions of `RewriteRuleSchema` exist:

- `src/execution/dynamic-rewriter.ts:10` — canonical, has `match: z.string().min(1, 'Regex pattern is required')`
- `src/skills/types.ts:8` — duplicate, has `match: z.string()` (no minimum length)

The `SkillFrontmatterSchema.rewrite_rules` field (in `types.ts`) validates parsed skill frontmatter using the weaker inline version. The `dynamicRewrite()` function receives rules already parsed by this weaker schema. If a skill frontmatter were ever written with an empty `match: ''`, it would pass schema validation in types.ts, then create `new RegExp('', 'i')` in the engine which matches every command — a correctness bug. While no current skills have this issue, the divergence is a maintainability and correctness risk.

### Gaps Summary

One structural gap was found: the `src/skills/types.ts` module was intended to import `RewriteRuleSchema` from `src/execution/dynamic-rewriter.ts` (key link specified in Plan 02). Instead, it retains the inline definition written before Plan 01 ran. The reconciliation step planned in Plan 03 was not executed.

The practical consequences are:
- Two maintenance surfaces for the same schema — rule changes to the canonical definition in `dynamic-rewriter.ts` will not automatically propagate to frontmatter validation
- The inline version is weaker (no `.min(1)` on `match`), creating a potential silent bug path if an empty match pattern enters a skill file
- The comment on line 6 of `types.ts` is factually stale

The fix is a 3-line change to `types.ts`: remove the inline schema block, add one import line. All other functionality is fully operational and tests pass.
