# Phase 12.1: Dynamic Command Rewriter - Research

**Researched:** 2026-03-14
**Domain:** Command rewriting engine, skill-driven execution pipeline
**Confidence:** HIGH

## Summary

The current command rewriting logic in `runner.ts` is hardcoded for PostgreSQL: `rewriteForContainer()` recognizes bare SQL (SELECT/SHOW/etc) and `psql` commands, wrapping them in `docker exec <container> psql -U postgres -c "..."`. The `stripHostFlag()` function removes `-h`/`--host` flags. This works perfectly for the Postgres scenario but cannot handle the Permission Trap's `chown` with `-u 0`, Docker Storage's `truncate` inside containers, or any future scenario without new TypeScript code.

The rewrite happens in **one place**: `debug.ts` line ~460, after the LLM generates a `StructuredDiagnosis`. The `fixPlan` steps get their commands rewritten via `rewriteForContainer()` before being returned to the client. Crucially, **the executor does NOT rewrite** -- it receives pre-rewritten commands from the `/debug` response and runs them verbatim via `parseCommand()` + `runCommand()`. This means the dynamic rewriter must integrate at the same point: between LLM output and plan delivery to the client/executor.

The skill context (which skill was selected) is available in `debug.ts` via `selection.skill` after `selectSkill()` runs. The skill's frontmatter is accessible as `selection.skill.frontmatter`. The Zod schema for frontmatter (`SkillFrontmatterSchema`) currently has no `rewrite_rules` field. Adding it with `.optional()` and a default of `[]` is backwards-compatible -- existing skills without the field will pass validation and get an empty rules array.

**Primary recommendation:** Create `src/execution/dynamic-rewriter.ts` as a pure function that takes a command + rewrite rules + discovered containers, returns a rewritten command. Wire it into `debug.ts` where `rewriteForContainer()` is currently called. Extend `SkillFrontmatterSchema` with an optional `rewrite_rules` array. Migrate all three existing skills. Keep `rewriteForContainer()` as dead code initially (remove in cleanup pass) to avoid breaking imports during development.

### Current Rewrite Flow (What Exists Today)
```
LLM generates StructuredDiagnosis
  -> debug.ts extracts fixPlan steps
  -> debug.ts calls rewriteForContainer(step.command, pgContainer) for EACH step
  -> Rewritten commands returned in /debug response
  -> /execute receives pre-rewritten commands, runs them verbatim
```

**Key insight:** Rewriting happens ONLY in `debug.ts` (line ~456-464), not in the executor. The executor calls `parseCommand()` + `runCommand()` on whatever command string it receives. This means the dynamic rewriter slots in at the same place.

### New Rewrite Flow (What We Build)
```
LLM generates StructuredDiagnosis or text diagnosis
  -> debug.ts extracts fixPlan steps
  -> debug.ts calls dynamicRewrite(step.command, skill.frontmatter.rewrite_rules, containers)
  -> Each rule matched by regex; first match wins
  -> Matched rule applies: strip_flags -> user escalation -> wrapper -> container wrapping
  -> Rewritten commands returned in /debug response
  -> /execute receives pre-rewritten commands, runs them verbatim (unchanged)
```

### Pattern 1: Pure Function Rewriter
**What:** `dynamicRewrite(command, rules, containers)` -- a stateless pure function
**When to use:** Every command in a fixPlan before returning to client
**Why pure:** Easy to test, no side effects, no dependency on skill registry at call site

```typescript
// src/execution/dynamic-rewriter.ts
import { z } from 'zod';

export const RewriteRuleSchema = z.object({
  match: z.string(),                         // Regex pattern string
  container: z.string().default('auto'),     // 'auto' or specific name
  user: z.string().optional(),               // e.g., '0' for root
  wrapper: z.string().optional(),            // e.g., 'psql -U postgres -c "{cmd}"'
  risk: z.enum(['read', 'write', 'destructive']).optional(),
  strip_flags: z.array(z.string()).optional(), // e.g., ['-h', '--host']
});

export type RewriteRule = z.infer<typeof RewriteRuleSchema>;

/**
 * Apply rewrite rules to a command. First matching rule wins.
 * If no rule matches, command passes through unchanged.
 */
export function dynamicRewrite(
  command: string,
  rules: RewriteRule[],
  containers: string[],
): string {
  const trimmed = command.trim();

  // Already wrapped in docker exec -- pass through
  if (/^docker\s+exec\b/.test(trimmed)) return trimmed;

  for (const rule of rules) {
    const regex = new RegExp(rule.match, 'i');
    if (!regex.test(trimmed)) continue;

    let cmd = trimmed;

    // 1. Strip flags first
    if (rule.strip_flags) {
      for (const flag of rule.strip_flags) {
        // Strip flag with value: -h <value>, --host <value>, --host=<value>
        const escaped = flag.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
        cmd = cmd.replace(new RegExp(`\\s+${escaped}\\s+\\S+`, 'g'), '');
        cmd = cmd.replace(new RegExp(`\\s+${escaped}=\\S+`, 'g'), '');
      }
      cmd = cmd.replace(/\s{2,}/g, ' ').trim();
    }

    // 2. Apply wrapper (e.g., psql -U postgres -c "{cmd}")
    if (rule.wrapper) {
      cmd = rule.wrapper.replace('{cmd}', cmd);
    }

    // 3. Resolve container
    const containerName = resolveContainer(rule.container, containers);
    if (!containerName) return cmd; // No container available, return as-is

    // 4. Build docker exec with optional -u flag
    const userFlag = rule.user ? `-u ${rule.user} ` : '';
    return `docker exec ${userFlag}${containerName} ${cmd}`;
  }

  // No rule matched -- pass through unchanged
  return trimmed;
}

function resolveContainer(spec: string, containers: string[]): string | undefined {
  if (spec === 'auto') {
    return containers[0]; // First container from discovery
  }
  // Specific container name -- verify it exists in discovered containers
  return containers.includes(spec) ? spec : containers[0];
}
```

### Anti-Patterns to Avoid
- **Adding rewrite logic to executor.ts:** The executor runs pre-rewritten commands. Keep it that way -- separation of concerns.
- **Making the rewriter stateful:** The rewriter should be a pure function. No class instances, no registry lookups at rewrite time.
- **Regex in YAML without escaping:** YAML requires double-backslash for regex escapes. `\b` must be written as `\\b` in YAML strings.
- **Forgetting the docker exec passthrough:** If the LLM already writes `docker exec ...`, the rewriter MUST NOT double-wrap it.

| Schema validation | Manual type checking | Zod schemas (existing) | Type-safe, composable, already used everywhere |

| Container resolution | Complex container matching per skill | `auto` keyword + `containers[0]` or `findDbContainer()` | Simple, covers all current scenarios |

**Key insight:** The entire feature is about moving configuration from TypeScript code to YAML frontmatter. The engine code should be minimal and generic.

## Common Pitfalls

### Pitfall 1: YAML Regex Escaping
**What goes wrong:** Writing `\b` in YAML results in a backspace character, not a word boundary.
**Why it happens:** YAML interprets `\b` as an escape sequence in double-quoted strings.
**How to avoid:** Use single-quoted YAML strings for regex patterns, or double-escape: `"^(SELECT|SHOW)\\b"`. In single-quoted YAML: `'^(SELECT|SHOW)\b'` works correctly because single-quoted strings don't process escapes.
**Warning signs:** Rewrite rules that should match don't match; regex patterns appear truncated.

### Pitfall 2: Double-Wrapping docker exec
**What goes wrong:** A command like `docker exec permission-app ls -ld /app/data` gets wrapped again into `docker exec permission-app docker exec permission-app ls -ld /app/data`.
**Why it happens:** The rewriter matches `ls` in the command after `docker exec`.
**How to avoid:** First check: if command starts with `docker exec`, return unchanged. This is already in the current `rewriteForContainer()` and must be preserved.
**Warning signs:** Commands failing with "docker: command not found" inside containers.

### Pitfall 3: Container Name Parsing from Discovery
**What goes wrong:** The `linux-filesystem-troubleshoot` discovery returns `"permission-app Exited (1) 30 seconds ago"` (name + status), not just the name.
**Why it happens:** Discovery command uses `docker ps -a --format "{{.Names}} {{.Status}}"` which includes status.
**How to avoid:** When parsing containers for the rewriter, split on space and take only the first token: `.split(' ')[0]`.
**Warning signs:** Container name resolves to `"permission-app Exited"` which Docker rejects.

### Pitfall 4: Rule Order Matters
**What goes wrong:** A broad rule like `match: ".*"` catches everything before specific rules run.
**Why it happens:** First-match-wins semantics.
**How to avoid:** Document that rules are evaluated in order; more specific rules MUST come first in the YAML array.
**Warning signs:** Commands getting wrong rewrite (e.g., a SELECT getting container exec without psql wrapper).

### Pitfall 5: Discovery Key Mismatch Between Skills
**What goes wrong:** Postgres discovery uses `"Running containers"` as key, but Permission Trap uses `"All containers with status"`.
**Why it happens:** Different `DISCOVERY_COMMANDS` entries have different labels.
**How to avoid:** The rewriter integration in debug.ts must check BOTH discovery keys when extracting container names, or normalize at discovery time.
**Warning signs:** `allContainers` array is empty for some skills, so no rewriting happens.

### Pitfall 6: Structured vs Text Diagnosis Paths
**What goes wrong:** Rewriting only applies to StructuredDiagnosis path (line ~456), missing the text diagnosis fallback.
**Why it happens:** Current code only rewrites inside the `if (structuredDiagnosis)` block.
**How to avoid:** Apply rewriting to ALL fixPlan steps regardless of how the diagnosis was generated. The fixPlan from `generateFixPlan()` also needs rewriting.
**Warning signs:** Commands work for Postgres (structured) but fail for other skills (text diagnosis).

## Open Questions

1. **Should rewriting apply to both StructuredDiagnosis AND text-generated fixPlans?**
   - What we know: Currently only StructuredDiagnosis fixPlans get rewritten (line ~460 in debug.ts). The `generateFixPlan()` fallback path (line ~510) does NOT rewrite.
   - What's unclear: The text diagnosis path generates fixPlans via the planning skill, which might already produce docker exec commands.
   - Recommendation: Apply rewriting to ALL fixPlan steps. If the command is already wrapped in docker exec, the passthrough check handles it. Belt-and-suspenders.

2. **Should `findDbContainer()` be used only for DB skills or generalized?**
   - What we know: `findDbContainer()` scans for postgres/mysql/redis patterns. For non-DB skills (permission-trap), the first container is the right target.
   - What's unclear: Future multi-container scenarios may need smarter container selection.
   - Recommendation: Use `container: auto` which resolves to `containers[0]`. For DB skills, the skill's frontmatter can list a specific container name or the integration code can pre-sort containers using `findDbContainer()`. Keep it simple for now -- this is deferred to v2.

3. **What about nginx-troubleshoot -- does it need rewrite_rules?**
   - What we know: The nginx skill's LLM already writes full `docker exec` commands. It doesn't need rewriting today.
   - Recommendation: Leave nginx-troubleshoot without rewrite_rules. The passthrough behavior (no rules = no rewriting) is correct.
