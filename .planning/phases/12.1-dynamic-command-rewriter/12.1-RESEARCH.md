# Phase 12.1: Dynamic Command Rewriter - Research (Expanded)

**Researched:** 2026-03-14 (expanded from initial research)
**Domain:** Universal command rewriting engine, skill-driven execution pipeline, safety model
**Confidence:** HIGH

## Summary

The current command rewriting logic in `runner.ts` is hardcoded for PostgreSQL: `rewriteForContainer()` recognizes bare SQL and psql commands, wrapping them in `docker exec <container> psql -U postgres -c "..."`. The `stripHostFlag()` function removes `-h`/`--host` flags. This works perfectly for the Postgres scenario but cannot handle the Permission Trap's `chown` with `-u 0`, Docker Storage's `truncate` inside containers, or any future scenario without new TypeScript code.

The rewrite happens in **one place**: `debug.ts` line ~460, after the LLM generates a `StructuredDiagnosis`. The `fixPlan` steps get their commands rewritten via `rewriteForContainer()` before being returned to the client. The executor does NOT rewrite -- it receives pre-rewritten commands and runs them verbatim via `parseCommand()` + `runCommand()`. This means the dynamic rewriter slots in at the same integration point.

**This expanded research addresses three questions the original did not:**
1. **Universality:** Can the rewriter handle ANY future scenario without new TypeScript?
2. **Safety:** If skills define rewrite rules, how do we prevent privilege escalation?
3. **Limits:** Where does the data-driven approach break down?

**Primary recommendation:** The regex-match + transform pipeline covers ~95% of foreseeable scenarios. The remaining 5% (host commands, multi-hop SSH, kubernetes) require a new concept: **execution context** (not just container wrapping). For Phase 12.1, implement the locked decisions as-is. The architecture naturally extends to execution contexts in a future phase without breaking changes.

## THE UNIVERSALITY QUESTION

### What "Universal" Actually Means

The user's question: "Can we make it so we NEVER have to write new TypeScript for new scenarios?"

**Answer: YES for all Docker-based scenarios. NOT YET for host/remote scenarios.**

The current architecture has one execution context: `docker exec <container> <command>`. Every rewrite rule ultimately produces a command that either:
1. Gets wrapped in `docker exec [flags] <container> <command>` (container context)
2. Passes through unchanged (already wrapped, or a host command like `docker restart`)

This covers every scenario where InfraBrain diagnoses problems inside Docker containers, which is the entire v1.x scope.

### Scenario Coverage Analysis

| Future Scenario | Needs New TS? | How It Works |
|----------------|---------------|--------------|
| MySQL troubleshoot | NO | `wrapper: 'mysql -u root -e "{cmd}"'`, `container: auto` |
| Redis troubleshoot | NO | `wrapper: 'redis-cli {cmd}'`, `container: auto` |
| MongoDB troubleshoot | NO | `wrapper: 'mongosh --eval "{cmd}"'`, `container: auto` |
| Nginx config check | NO | Already writes full docker exec commands, no rules needed |
| Log rotation | NO | `match: "^truncate"`, `container: auto`, `risk: write` |
| Container health checks | NO | `match: "^(curl|wget)"`, `container: auto`, `risk: read` |
| File editing inside container | NO | `match: "^sed"`, `container: auto`, `user: "0"`, `risk: write` |
| Process management in container | NO | `match: "^kill"`, `container: auto`, `user: "0"`, `risk: destructive` |
| Systemd service restart (host) | NO | Command is `systemctl restart X` -- passes through unchanged (no container) |
| Docker compose operations | NO | Command is `docker compose restart` -- passes through unchanged |
| Kubernetes pod exec | **FUTURE** | Needs `kubectl exec` context, not `docker exec` |
| SSH to remote host | **FUTURE** | Needs SSH execution context |
| Multi-container pipe | **FUTURE** | Needs command chaining across containers |

**Key insight:** The "pass-through for unmatched commands" behavior is itself a universality feature. Commands that don't need rewriting (docker restart, docker logs, curl to host) already work because they pass through unchanged. The rewriter only activates when a skill declares rules AND a command matches a rule pattern.

### The 95/5 Split

**95% covered (Docker container execution):**
- Any command that needs to run inside a container with optional user escalation and/or wrapper
- Any command that needs flag stripping before container injection
- Any command that already includes `docker exec` (passthrough)
- Any host-level command (docker restart, docker logs, systemctl -- passthrough)

**5% not covered (requires future execution context concept):**
- `kubectl exec -it <pod> -- <command>` (Kubernetes)
- `ssh <host> <command>` (remote execution)
- Multi-container orchestration (run command in container A, pipe result to container B)
- Commands requiring environment variables inside the container (`docker exec -e VAR=val`)

### Why the 5% Doesn't Block Phase 12.1

The locked decisions specify three rewrite capabilities: container wrapping, privilege escalation, command wrapping. These three are sufficient for ALL current and near-future Docker scenarios. The architecture naturally extends:

```yaml
# Future (v2+) -- NOT for Phase 12.1
rewrite_rules:
  - match: "^SELECT"
    context: kubernetes     # NEW: execution context type
    pod: auto
    namespace: default
    wrapper: 'psql -U postgres -c "{cmd}"'
```

Adding `context: docker` (default) vs `context: kubernetes` vs `context: host` is a backwards-compatible extension. Skills without `context` get `docker` implicitly.

## THE SAFETY QUESTION

### Threat Model: What Could Go Wrong?

If skills define rewrite rules in YAML, a malicious or broken skill could:

1. **Escalate privileges:** `user: "0"` on every command -- runs everything as root inside containers
2. **Target wrong container:** `container: "production-db"` instead of `auto` -- commands hit the wrong target
3. **Wrap destructively:** `wrapper: 'rm -rf / && {cmd}'` -- injection via wrapper template
4. **Match too broadly:** `match: ".*"` with `user: "0"` -- every command gets root escalation
5. **Strip safety-critical flags:** `strip_flags: ["--dry-run"]` -- removes safety nets

### Defense Layers (Belt-and-Suspenders-and-Vest)

**Layer 1: Skill Files Are Static Code, Not User Input**

Skills are `.md` files in the `skills/` directory, loaded at server startup by `loadSkillDirectory()`. They are NOT uploaded by users, NOT generated by LLMs, NOT modified at runtime. They are version-controlled code written by the InfraBrain developers. This is the same trust level as TypeScript source code.

**Implication:** A "malicious skill" requires a malicious commit to the repository. This is the same threat as malicious TypeScript code -- the rewrite rules don't create a new attack surface.

**Layer 2: Zod Schema Validation**

The `RewriteRuleSchema` constrains what a rule CAN express:

```typescript
export const RewriteRuleSchema = z.object({
  match: z.string(),                         // Must be valid string (Zod validates)
  container: z.string().default('auto'),     // Limited to string
  user: z.string().optional(),               // Only string, not arbitrary flags
  wrapper: z.string().optional(),            // Template string
  risk: z.enum(['read', 'write', 'destructive']).optional(),
  strip_flags: z.array(z.string()).optional(),
});
```

The schema prevents:
- Non-string values in any field
- Invalid risk levels
- Arbitrary nested objects or code execution

The schema does NOT prevent: malicious string values (e.g., `wrapper: 'rm -rf /'`). But Layer 3 catches this.

**Layer 3: Safety Validator Runs AFTER Rewriting (The Real Firewall)**

This is the critical safety guarantee. After the rewriter produces a final command string, `validateCommand()` in `validator.ts` runs:

1. `sanitizeDockerExec()` -- strips `-it`/`-t` flags
2. `BLOCKED_PATTERNS` -- hardcoded, non-overridable:
   - `rm -rf /` -- blocked
   - `mkfs.*` -- blocked
   - `dd if=... of=/dev/...` -- blocked
   - Fork bomb -- blocked
   - `chmod -R 777 /` -- blocked
3. Package manager patterns -- blocked
4. Config blocklist -- checked
5. Config allowlist -- enforced if present
6. `classifyCommand()` -- risk level assigned

**Even if a rewrite rule produces `docker exec container rm -rf /`, the safety validator blocks it.** The rewriter cannot bypass BLOCKED_PATTERNS because those are hardcoded in `rules.ts` and checked on the FINAL command string.

**Layer 4: HITL Approval Gate**

The executor (`executor.ts` line ~146) calls `requestApproval(step.command, step.risk)` for EVERY step. The human admin sees the rewritten command and its risk level. Even if a command passes the safety validator, the admin can reject it.

**Layer 5: Damage Budget**

The damage budget (`DamageBudget`) limits total destructive operations per session. Even if a skill has many write/destructive rules, the budget caps cumulative damage.

### Safety Invariants (Must Hold True)

| Invariant | Enforced By | Can Rewriter Break It? |
|-----------|-------------|----------------------|
| `rm -rf /` never executes | BLOCKED_PATTERNS in validator.ts | NO -- checked on final command |
| No package installation | PACKAGE_MANAGER_PATTERN in validator.ts | NO -- checked on final command |
| Human sees every command | executor.ts requestApproval() | NO -- rewriter runs before executor |
| Budget limits damage | DamageBudget in executor.ts | NO -- budget checks final risk level |
| No fork bombs | BLOCKED_PATTERNS in validator.ts | NO -- checked on final command |

### The User Escalation Question

`user: "0"` means "run as root inside the container." Is this dangerous?

**Context:** `docker exec` already runs as root by default (unless the container's Dockerfile sets a USER). The `-u 0` flag is explicit about what docker exec does implicitly. The real danger isn't root-inside-container (which is sandboxed by Docker's namespace isolation) -- it's root-on-host, which requires `--privileged` or volume mounts to `/`, neither of which the rewriter can add.

**Conclusion:** `user: "0"` is safe within Docker's security model. The rewriter cannot escape the container sandbox.

### Wrapper Injection Analysis

Could `wrapper: 'malicious && {cmd}'` inject commands?

Yes, the wrapper template is string interpolation. If a skill author writes `wrapper: 'rm -rf / && {cmd}'`, the resulting command would be `docker exec container rm -rf / && <original-cmd>`. However:

1. The safety validator checks the FULL command string -- `rm -rf /` would be caught by BLOCKED_PATTERNS
2. The `needsShell()` function in `runner.ts` detects `&&` and pipes, flagging shell mode
3. The human admin sees the full command before approval

**Recommendation for Phase 12.1:** Add a Zod refinement to reject wrappers containing shell metacharacters (`&&`, `||`, `;`, `|`, backticks). This is defense-in-depth:

```typescript
wrapper: z.string().optional().refine(
  (w) => !w || !/[;&|`$]/.test(w.replace('{cmd}', '')),
  'Wrapper must not contain shell metacharacters (;, &, |, `, $) outside {cmd} placeholder'
),
```

### Safety Verdict

**The rewriter does NOT create new attack surface.** Skill files are developer-written code (same trust as TypeScript). The safety validator, BLOCKED_PATTERNS, HITL approval, and damage budget all operate on the FINAL rewritten command. The rewriter is a transform layer between LLM output and the existing safety pipeline -- it cannot bypass any safety check.

## THE LIMITS QUESTION

### Where Data-Driven Rewriting Breaks Down

**Limit 1: Semantic Understanding**

The rewriter does pattern matching (`match: regex`). It does NOT understand what a command does. Example:

```bash
# These both match "^cat" but have very different implications:
cat /etc/shadow          # Security-sensitive file read
cat /var/log/app.log     # Harmless log read
```

The rewriter treats both identically. The SAFETY VALIDATOR handles the distinction via allowlists/blocklists. This is correct -- the rewriter's job is wrapping, not classification.

**Limit 2: Command Arguments That Change Meaning**

```bash
chmod 755 /app/data      # Safe: standard permissions
chmod 777 /               # Dangerous: world-writable root
```

Both match `^chmod`. The rewriter wraps both in `docker exec -u 0 container chmod ...`. The safety validator catches `chmod -R 777 /` but not all dangerous chmod variants.

**This is fine.** The rewriter is a transport layer. Safety classification happens downstream.

**Limit 3: Multi-Container Commands**

```bash
# Copy file from container A to container B
docker cp containerA:/data/file.txt /tmp/
docker cp /tmp/file.txt containerB:/data/
```

The rewriter handles single-container targeting. Multi-container workflows require multiple separate commands, which the LLM generates as multiple fixPlan steps. Each step gets rewritten independently. This works today without changes.

**Limit 4: Environment Variables**

```bash
# Some commands need env vars inside the container
PGPASSWORD=secret psql -U admin -d mydb -c "SELECT 1"
```

The current rewrite rule cannot inject `-e PGPASSWORD=secret` into the docker exec command. However, InfraBrain's philosophy is to use local unix sockets (no password needed) inside containers. This is a deliberate design choice, not a limitation.

**If needed in v2:** Add optional `env` field to rewrite rules:
```yaml
env:
  PGPASSWORD: "secret"
```
This maps to `docker exec -e PGPASSWORD=secret container ...`.

**Limit 5: Commands That Need stdin/TTY**

```bash
# Interactive commands don't work with docker exec (non-interactive)
psql    # Opens interactive shell -- BROKEN
mysql   # Opens interactive shell -- BROKEN
```

InfraBrain already handles this: the safety validator strips `-it`/`-t` flags, and all commands use `-c` or `-e` flags for non-interactive execution. The wrapper pattern enforces this naturally:
- `wrapper: 'psql -U postgres -c "{cmd}"'` -- forces non-interactive mode.

**Limit 6: Host Commands (systemctl, iptables, etc.)**

Commands that run on the HOST, not inside a container, don't need rewriting. They pass through unchanged because no rewrite rule matches. This is correct behavior TODAY.

However, if a future skill wants to rewrite host commands (e.g., strip certain flags from `systemctl`), the current architecture supports this -- just don't specify `container`:

```yaml
# Hypothetical future rule -- flag stripping without container wrapping
rewrite_rules:
  - match: "^systemctl restart"
    strip_flags: ["--force"]
    risk: write
    # No container field = no docker exec wrapping
```

**Recommendation:** In the `dynamicRewrite()` function, if `container` is not specified (or empty string), apply strip_flags and wrapper but skip the docker exec wrapping. This makes the rewriter universal for ANY command, not just containerized ones.

### What This Means for the Planner

The dynamic rewriter as designed in the locked decisions handles 100% of current InfraBrain scenarios and ~95% of foreseeable future scenarios. The 5% gap (Kubernetes, SSH, multi-hop) is a future execution-context abstraction, not a rewriter limitation.

### Pattern 1: Pure Function Rewriter
**What:** `dynamicRewrite(command, rules, containers)` -- a stateless pure function
**When to use:** Every command in a fixPlan before returning to client
**Why pure:** Easy to test, no side effects, no dependency on skill registry at call site

```typescript
// src/execution/dynamic-rewriter.ts
import { z } from 'zod';

export const RewriteRuleSchema = z.object({
  match: z.string(),                         // Regex pattern string
  container: z.string().default('auto'),     // 'auto', specific name, or '' for no container
  user: z.string().optional(),               // e.g., '0' for root
  wrapper: z.string().optional().refine(
    (w) => !w || !/[;&|`$]/.test(w.replace('{cmd}', '')),
    'Wrapper must not contain shell metacharacters outside {cmd} placeholder'
  ),
  risk: z.enum(['read', 'write', 'destructive']).optional(),
  strip_flags: z.array(z.string()).optional(), // e.g., ['-h', '--host']
});

export type RewriteRule = z.infer<typeof RewriteRuleSchema>;

/**
 * Apply rewrite rules to a command. First matching rule wins.
 * If no rule matches, command passes through unchanged.
 *
 * Transform order: strip_flags -> wrapper -> docker exec (user + container)
 * This order ensures flags are stripped from the ORIGINAL command,
 * wrapper wraps the cleaned command, and docker exec wraps everything.
 */
export function dynamicRewrite(
  command: string,
  rules: RewriteRule[],
  containers: string[],
): string {
  const trimmed = command.trim();

  // Already wrapped in docker exec -- pass through
  if (/^docker\s+exec\b/.test(trimmed)) return trimmed;

  for (const rule of rules) {
    const regex = new RegExp(rule.match, 'i');
    if (!regex.test(trimmed)) continue;

    let cmd = trimmed;

    // 1. Strip flags first (operates on original command)
    if (rule.strip_flags) {
      for (const flag of rule.strip_flags) {
        const escaped = flag.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
        cmd = cmd.replace(new RegExp(`\\s+${escaped}\\s+\\S+`, 'g'), '');
        cmd = cmd.replace(new RegExp(`\\s+${escaped}=\\S+`, 'g'), '');
      }
      cmd = cmd.replace(/\s{2,}/g, ' ').trim();
    }

    // 2. Apply wrapper (e.g., psql -U postgres -c "{cmd}")
    if (rule.wrapper) {
      cmd = rule.wrapper.replace('{cmd}', cmd);
    }

    // 3. Container wrapping (skip if container is empty/absent -- host command)
    const containerSpec = rule.container ?? 'auto';
    if (containerSpec === '' || containerSpec === 'none') {
      // No container wrapping -- return command with strip_flags and wrapper applied
      return cmd;
    }

    const containerName = resolveContainer(containerSpec, containers);
    if (!containerName) return cmd; // No container available, return as-is

    // 4. Build docker exec with optional -u flag
    const userFlag = rule.user ? `-u ${rule.user} ` : '';
    return `docker exec ${userFlag}${containerName} ${cmd}`;
  }

  // No rule matched -- pass through unchanged
  return trimmed;
}

function resolveContainer(spec: string, containers: string[]): string | undefined {
  if (containers.length === 0) return undefined;
  if (spec === 'auto') {
    return containers[0]; // First container from discovery
  }
  // Specific container name -- verify it exists in discovered containers
  return containers.includes(spec) ? spec : containers[0];
}
```

**What:** Rules without `container` (or `container: ""`) apply transforms without docker exec wrapping
**Why:** Makes the rewriter universal for ANY command, not just containerized ones

### Anti-Patterns to Avoid
- **Adding rewrite logic to executor.ts:** The executor runs pre-rewritten commands. Keep it that way -- separation of concerns.
- **Making the rewriter stateful:** The rewriter should be a pure function. No class instances, no registry lookups at rewrite time.
- **Regex in YAML without escaping:** YAML requires double-backslash for regex escapes. `\b` must be written as `\\b` in YAML strings.
- **Forgetting the docker exec passthrough:** If the LLM already writes `docker exec ...`, the rewriter MUST NOT double-wrap it.
- **Putting safety logic in the rewriter:** The rewriter transforms. The validator validates. Never mix these concerns.
- **Shell metacharacters in wrappers:** The wrapper Zod refinement rejects `&&`, `||`, `;`, `|`, backticks to prevent injection.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| YAML parsing | Custom YAML parser | gray-matter (existing) | Already handles frontmatter perfectly |
| Schema validation | Manual type checking | Zod schemas (existing) | Type-safe, composable, already used everywhere |
| Regex flag stripping | Custom string manipulation per flag | Generic strip loop | The current `stripHostFlag()` is hardcoded for `-h`/`--host` -- generalize via `strip_flags` array |
| Container resolution | Complex container matching per skill | `auto` keyword + `containers[0]` or `findDbContainer()` | Simple, covers all current scenarios |
| Safety enforcement | Custom safety checks in rewriter | Existing validator.ts pipeline | BLOCKED_PATTERNS, allowlists, classifyCommand already handle everything |
| Command injection prevention | Custom sanitizer in rewriter | Zod refinement on wrapper field | Reject shell metacharacters at schema validation time |

**Key insight:** The entire feature is about moving configuration from TypeScript code to YAML frontmatter. The engine code should be minimal and generic. The safety pipeline is already robust and runs AFTER rewriting.

## Common Pitfalls

### Pitfall 1: YAML Regex Escaping
**What goes wrong:** Writing `\b` in YAML results in a backspace character, not a word boundary.
**Why it happens:** YAML interprets `\b` as an escape sequence in double-quoted strings.
**How to avoid:** Use double-escaped regex in YAML: `"^(SELECT|SHOW)\\b"`. In YAML double-quoted strings, `\\b` produces the literal `\b` that regex needs.
**Warning signs:** Rewrite rules that should match don't match; regex patterns appear truncated.

### Pitfall 2: Double-Wrapping docker exec
**What goes wrong:** A command like `docker exec permission-app ls -ld /app/data` gets wrapped again.
**Why it happens:** The rewriter matches `ls` in the command after `docker exec`.
**How to avoid:** First check: if command starts with `docker exec`, return unchanged. This is already in the code pattern above.
**Warning signs:** Commands failing with "docker: command not found" inside containers.

### Pitfall 3: Container Name Parsing from Discovery
**What goes wrong:** The `linux-filesystem-troubleshoot` discovery returns `"permission-app Exited (1) 30 seconds ago"` (name + status), not just the name.
**Why it happens:** Discovery command uses `docker ps -a --format "{{.Names}} {{.Status}}"` which includes status.
**How to avoid:** When parsing containers for the rewriter, split on space and take only the first token: `.split(/\s+/)[0]`.
**Warning signs:** Container name resolves to `"permission-app Exited"` which Docker rejects.

### Pitfall 4: Rule Order Matters
**What goes wrong:** A broad rule like `match: ".*"` catches everything before specific rules run.
**Why it happens:** First-match-wins semantics.
**How to avoid:** Document that rules are evaluated in order; more specific rules MUST come first in the YAML array.
**Warning signs:** Commands getting wrong rewrite (e.g., a SELECT getting container exec without psql wrapper).

### Pitfall 5: Discovery Key Mismatch Between Skills
**What goes wrong:** Postgres discovery uses `"Running containers"` as key, but Permission Trap uses `"All containers with status"`.
**Why it happens:** Different `DISCOVERY_COMMANDS` entries have different labels.
**How to avoid:** The container extraction function must check BOTH discovery keys:
```typescript
function extractContainerNames(discoveryRaw: Record<string, string>): string[] {
  const raw = discoveryRaw['Running containers']
    ?? discoveryRaw['All containers with status']
    ?? '';
  return raw.split('\n').map(line => line.trim().split(/\s+/)[0]).filter(Boolean);
}
```
**Warning signs:** `allContainers` array is empty for some skills, so no rewriting happens.

### Pitfall 6: Structured vs Text Diagnosis Paths
**What goes wrong:** Rewriting only applies to StructuredDiagnosis path, missing the text diagnosis fallback.
**Why it happens:** Current code only rewrites inside the `if (structuredDiagnosis)` block (line ~460).
**How to avoid:** Apply rewriting to ALL fixPlan steps regardless of how the diagnosis was generated. The `generateFixPlan()` fallback path (line ~510) also produces fixPlans that need rewriting.
**Warning signs:** Commands work for Postgres (structured) but fail for other skills.

### Pitfall 7: Wrapper {cmd} Placeholder With Special Characters
**What goes wrong:** If the original command contains `"` and the wrapper uses `'psql -U postgres -c "{cmd}"'`, the nested quotes break.
**Why it happens:** String interpolation without escaping inner quotes.
**How to avoid:** When the wrapper contains `{cmd}` inside quotes, the command should have internal quotes escaped. For SQL, the current `rewriteForContainer()` strips trailing semicolons. The dynamic rewriter should do the same for SQL wrappers.
**Warning signs:** `psql -c "SELECT "value" FROM..."` produces a parse error.

### Pitfall 8: Regex ReDoS (Denial of Service via Regex)
**What goes wrong:** A pathological regex in a skill's `match` field causes catastrophic backtracking.
**Why it happens:** Nested quantifiers like `(a+)+$` can cause exponential time on certain inputs.
**How to avoid:** All current skill regexes are simple anchored patterns (`^(SELECT|SHOW)\\b`). Add a timeout or complexity limit if allowing user-contributed skills in the future. For Phase 12.1, this is not a risk since skills are developer-written.
**Warning signs:** Rewriter hangs on certain commands.

### Rewriter with findDbContainer for DB Skills
```typescript
// In debug.ts, determine container ordering based on skill type
function resolveContainersForSkill(
  containers: string[],
  skill: SkillFile,
): string[] {
  // DB skills should prioritize the DB container
  if (skill.frontmatter.tools.includes('psql') || skill.frontmatter.preferred_model === 'forensic') {
    const dbContainer = findDbContainer(containers);
    if (dbContainer) {
      return [dbContainer, ...containers.filter(c => c !== dbContainer)];
    }
  }
  return containers;
}
```

## Open Questions

1. **Should rewriting apply to both StructuredDiagnosis AND text-generated fixPlans?**
   - What we know: Currently only StructuredDiagnosis fixPlans get rewritten (line ~460). The `generateFixPlan()` fallback path (line ~510) does NOT rewrite.
   - Recommendation: YES -- apply rewriting to ALL fixPlan steps. The docker exec passthrough check handles already-wrapped commands. Belt-and-suspenders.

2. **Should `findDbContainer()` be used only for DB skills or generalized?**
   - What we know: `findDbContainer()` scans for postgres/mysql/redis patterns. For non-DB skills, `containers[0]` is the right target.
   - Recommendation: Use `resolveContainersForSkill()` which pre-sorts containers for DB skills and uses natural order for others.

3. **Should the wrapper Zod refinement block shell metacharacters?**
   - What we know: A wrapper like `cmd1 && {cmd}` could inject commands before the user's command.
   - Recommendation: YES -- add the refinement. Defense-in-depth. The safety validator would catch most cases, but blocking at schema level is cleaner.

4. **What happens when a command needs quoting inside a wrapper?**
   - What we know: `psql -U postgres -c "{cmd}"` works when `{cmd}` is `SELECT 1` but breaks when `{cmd}` contains double quotes.
   - What's unclear: How the current `rewriteForContainer()` handles this (it wraps in `"..."` directly).
   - Recommendation: For Phase 12.1, match current behavior. SQL commands rarely contain double quotes. Flag for v2 if issues arise.

5. **Should container: "none" / container: "" be a Phase 12.1 feature?**
   - What we know: It enables host-command rewriting without new TS code. It is 3 lines of code in the rewriter.
   - Recommendation: YES -- include it. The `containerSpec === '' || containerSpec === 'none'` check is trivial and makes the rewriter truly universal. No skills use it yet, so no migration needed.
