<objective>
Build the D-3 reader: a pure module that derives a step's outcome exclusively from its event
sequence, enforces terminal-event cardinality, and surfaces violations rather than resolving them.

Purpose: D-3 is LOCKED and is the rule that prevents the original defect from returning. Interpreting
ambiguity away is precisely how a failure came to render as a success; a rule that silently repairs
its own violations cannot be relied upon. This module must therefore be willing to return "I cannot
tell" as a first-class answer.

This is a NEW module. `src/ui/App.tsx` and `src/cli/formatter.ts` are frozen by criterion 8, so the
derivation cannot live in either of them.

Output: `src/audit/step-status.ts`, its test suite, and the committed pre-fix fixture that
criterion 7 needs.
</objective>

<critical_notices>
**Do NOT apply the cardinality invariant to pre-fix records.** Pre-fix records have no attempt key
and `step_failed` was never emitted in that era — there are 123 historical `step_complete` records
and ZERO historical `step_failed` records. Applying the invariant to them would flag every one of
those 123 records as an integrity violation. Era detection runs FIRST, and pre-fix records are
returned as recorded and marked as such. D-1 forbids reinterpreting them.

**Never read `self_heal_attempt` for status.** It is the LLM-correction rationale record, not an
outcome record. It carries no `stepIndex` in any of the 98 historical records, so it never was an
attributable outcome. The step-event family is the sole input to status derivation. This precedence
rule must be enforced by a test, not just documented.

**Never infer status from absence.** There must be no code path in which "no failure event was
seen" yields a successful status. That inference is the root cause this phase exists to abolish.

**Suite baseline:** 3 failures expected (2 environmental POCs + the intentional RED test from plan
20-01). Do not fix, skip, or delete `tests/execution/audit-step-events.test.ts`.

  <behavior>
    Era detection:
    - A step event whose `metadata.attempt_n` is not a number is a PRE-FIX record. It is reported
      with era `pre_fix`, its status is reported as recorded, and no cardinality verdict is applied.
    - A step event with a numeric `metadata.attempt_n` is a POST-FIX record and the cardinality
      invariant applies.

    Cardinality, for post-fix records grouped by `(stepIndex, attempt_n)`:
    - Exactly one terminal event: `succeeded` for a completion, `failed` for a failure.
    - Two or more terminal events: `integrity_violation`, ALWAYS, regardless of what those events
      say. The conflicting events are carried in the result so the violation is inspectable.
    - Zero terminal events and the session is demonstrably closed: `integrity_violation`.
    - Zero terminal events and the session is demonstrably open: `in_flight`.
    - Zero terminal events and the session state is unknowable: `indeterminate`.

    Session-closed detection:
    - Presence of any of `execution_complete`, `lock_released` or `session_end` means closed.
    - Presence of `execution_start` with none of those markers means open.
    - Absence of all of them, including `execution_start`, means unknowable.

    Precedence:
    - A `self_heal_attempt` with an outcome of success, contradicting a `step_failed` for the same
      step and attempt, yields `failed`. The step family wins, always.

    Step roll-up:
    - A step's status is the state of its HIGHEST `attempt_n`, with lower attempts retained as the
      attempt history.
    - If ANY attempt for a step is `integrity_violation`, the step is `integrity_violation`. A
      violation is never absorbed by a later plausible-looking outcome.

    Never-infer-from-absence:
    - There is no input for which the absence of a failure event alone produces `succeeded`.
  </behavior>
