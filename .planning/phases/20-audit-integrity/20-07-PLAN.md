<objective>
Make the self-heal retry loop leave an attempt record for every attempt it makes.

A step that self-healed after three attempts currently leaves exactly one clean completion record.
Across all recorded history there are 123 completion records, 98 self-heal records, 30 exhaustion
records, 26 breaker records — and zero step failure records. The attempt history is discarded at the
moment it is most interesting.

Purpose: criterion 2 requires a failure record on every failing attempt, explicitly including
attempts that a later retry or self-heal ultimately rescues. Those attempts happen inside
`selfHealStep`, which returns its `attempts[]` array only after the fact, so the emission must
happen at the true moment of each attempt — which is exactly where the four existing self-heal
records are already written.

Output: attempt-numbered step events at the self-healer's four existing emission sites, plus a join
key on the self-heal record itself.
</objective>

<critical_notices>
**The self-heal record and the step-event family COEXIST. This was settled empirically, not by
preference.** `self_heal_attempt` carries no `stepIndex` in any of the 98 historical records, so it
never was an attributable outcome record and cannot become one without reinterpreting history that
D-1 protects. The division of responsibility is:

| Family | Owns | Never used for |
|---|---|---|
| step start / complete / failed | The canonical outcome record and the SOLE input to status derivation | — |
| self-heal record | The LLM-correction rationale: what the model was given, what it produced, whether safety blocked it, whether the error type shifted | Status. Ever. |

**Do NOT reuse the existing `attempt` field as the global attempt number.** It is computed as
`attempts.length + 1` and counts heal-loop iterations only. The executor's own first execution is
not among them, so a value of 1 in that field denotes global attempt 2. Reusing it would off-by-one
the entire new schema. Add the new number alongside it; change neither the old field's name nor its
value.

**Do NOT remove `outcome`, `stderr` or `exitCode` from the self-heal record.** Removing them is a
behaviour change with no consumer benefit and unknown blast radius, and it would not eliminate the
duplication trap anyway. The trap is two sources of truth for STATUS, not two records mentioning the
same command, and it is closed by the precedence rule plan 20-05 enforces with a test.

**Type gate for this file is a BASELINE DIFF, not zero.** `src/execution/self-healer.ts` carries 2
of the 8 pre-existing project tsc errors — both `TS2353: 'maxTokens' does not exist`, at roughly
lines 252 and 369, from AI SDK v6 drift (dossier section C). The gate is: exactly 2 errors, still the
same 2. Never gate on a bare project-wide `npx tsc --noEmit`; it cannot pass.

**Suite baseline:** the intentional RED test from plan 20-01 is still expected to fail until plan
20-08. Do not edit `tests/execution/audit-step-events.test.ts`.
</critical_notices>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM-corrected command -> execution | Model-generated commands run against real infrastructure |
| heal-loop attempt -> audit record | The only moment a rescued step's failures can be captured |
| self-heal rationale record -> status derivation | A second narrative that must never be treated as authoritative |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-25 | Repudiation | rescued step hides the attempts it took | critical | mitigate | Failure events at all three failing sites, proven by a test where the first correction fails and the second succeeds and the failure record survives |
| T-20-26 | Repudiation | duplicate terminal event from the success site | high | mitigate | The success site emits no step terminal event by explicit instruction, asserted by test; the executor owns the step's single completion event |
| T-20-27 | Spoofing | rationale record mistaken for an outcome record | high | mitigate | Division of responsibility documented in code and enforced by plan 20-05's contradiction test; the record gains a join key rather than authority |
| T-20-28 | Repudiation | off-by-one attempt numbering | high | mitigate | The pre-existing loop-local counter is left untouched and a distinct global number is derived from `attemptBase`; pinned by a test that varies the base |
| T-20-29 | Tampering | safety-blocked correction omitted from the record | medium | mitigate | A safety-blocked iteration consumed budget and an attempt slot, so it emits a failure event with its own classification rather than being silently skipped |
</threat_model>
