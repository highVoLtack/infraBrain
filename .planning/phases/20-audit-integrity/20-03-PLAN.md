<objective>
Build the typed emitter that makes the D-2 producer invariant unforgettable, and close the
same-millisecond ordering hazard that would otherwise let this fix invert its own result.

Purpose: D-2 requires `attempt_n` on every step event with no exceptions, including attempt 1,
because "no `attempt_n` implies a pre-fix record" is the ONLY thing distinguishing the two schema
eras that D-1 keeps alive in the same log. A single new event without it collapses the
discriminant. This plan makes the invariant structural rather than remembered.

Output: `StepEventType`, `StepEventPayload`, `AuditLogger.logStepEvent`, and a monotonic timestamp
source. No emission sites change yet.
</objective>

<critical_notices>
**`attempt_n` MUST live inside `metadata`. This is not a preference.**
`WriteThrough.appendAudit` (`src/state/store.ts:185-209`) writes the whole entry to `audit.jsonl`
via `JSON.stringify(entry)` but INSERTs into SQLite with a FIXED column list. `queryAuditLog`
(`store.ts:171-182`) rebuilds entries from those columns only. Replay reads SQLite via
`GET /history`. A top-level `AuditEntry.attempt_n` would survive in the file and be **silently
dropped on the exact path replay uses** — present on disk, absent in the UI, no error anywhere.
That is a worse failure mode than the bug being fixed. `metadata` is serialized whole and parsed
whole, so it survives both paths.

**Do NOT narrow `logExecution` in this plan.** Narrowing it to
`Exclude<AuditEventType, StepEventType>` is the criterion-3 compile-time guarantee, but
`src/execution/executor.ts:341` still passes a step event type to `logExecution` today. Narrowing
now would break the build. The narrowing lands in plan 20-08, after every emission site has
migrated. This plan is purely ADDITIVE.

**Suite baseline:** 3 failures expected (2 environmental POCs + the intentional RED test from plan
20-01). Do not fix, skip, or delete `tests/execution/audit-step-events.test.ts`.
</critical_notices>

  <name>Task 3: Make audit timestamps strictly increasing per logger instance</name>

  <read_first>
    - `src/audit/logger.ts` lines 79-86 — `private log`, where `new Date().toISOString()` is called
      at line 81.
    - `src/ui/App.tsx` lines 114-119 — READ ONLY. `buildReplayState` sorts entries by timestamp

    - `src/state/store.ts` line 168 — `ORDER BY timestamp DESC`.
    - `.planning/phases/20-audit-integrity/20-RESEARCH.md` "Pitfall 1" — the full derivation.
  </read_first>

  <behavior>
    - Two audit events emitted in the same millisecond receive strictly increasing ISO timestamps.
    - Timestamps never move backwards, even if the system clock does.
    - Timestamps remain valid ISO-8601 strings with millisecond precision.
    - A single event's timestamp is still approximately wall-clock now (the correction is a
      one-millisecond nudge, not an offset that accumulates unboundedly under normal load).
  </behavior>

  <files>src/audit/logger.ts, tests/audit/logger.test.ts</files>

  <action>
    Replace the direct `new Date().toISOString()` call in `private log` with a private monotonic
    timestamp source on the `AuditLogger` instance.

    The mechanism: keep a private `lastTimestampMs` field initialized to 0. On each call take
    `Date.now()`; if it is less than or equal to `lastTimestampMs`, use `lastTimestampMs + 1`
    instead. Store the resulting value back into `lastTimestampMs` and return it as an ISO string.

    Why this is load-bearing, and why it belongs in the producer: `queryAuditLog` returns rows
    `ORDER BY timestamp DESC`, and `buildReplayState` re-sorts them ascending with a STABLE sort.
    For two events sharing an identical millisecond timestamp, a stable sort preserves their arrival
    order — which is descending. Once this phase makes a failure event and a success event adjacent
    for the same step, a step rescued on its second attempt would replay as FAILED: the exact mirror
    image of the bug this phase exists to fix. The consumer is frozen by criterion 8, so the
    ordering must be guaranteed at emission. This is reachable in tests today, not theoretical —
    `retryDelayMs: 0` plus a mocked runner resolves attempts within one millisecond.

    Scope note: this changes the timestamp behaviour of EVERY audit event, not only step events.
    That is intended and correct. Run the full suite and confirm no existing test asserted an exact
    timestamp equality that this breaks.

    Add tests to `tests/audit/logger.test.ts` that:
    - Emit several events back to back in a tight loop and assert every timestamp is strictly
      greater than its predecessor when parsed to epoch milliseconds.
    - Emit two events with `Date.now` stubbed to a constant value and assert the second timestamp is
      exactly one millisecond after the first.
    - Assert every produced timestamp still parses as a valid date and matches ISO-8601 with
      milliseconds.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| producer code -> AuditLogger | The last point at which a malformed record can be refused |
| AuditLogger -> JSONL file and SQLite | Two write targets with different fidelity; fields can be lost between them |
| stored record -> auditor / pilot engineer | The reader cannot tell a dropped field from a field that was never true |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-07 | Repudiation | step event without `attempt_n` | critical | mitigate | Required field on `StepEventPayload` plus a runtime guard that throws; a step event with no attempt number cannot be written by either a typed or an untyped caller |
| T-20-08 | Information disclosure | field silently dropped by the SQLite insert | high | mitigate | `attempt_n` is placed inside `metadata`, the only column that round-trips whole; a test asserts it survives a JSON stringify/parse cycle and that it is absent from the entry's top level |
| T-20-09 | Tampering | same-millisecond event reordering | high | mitigate | Per-instance monotonic timestamp source guarantees strict ordering at emission, so the frozen consumer's stable sort cannot invert a failure and a success |
| T-20-10 | Repudiation | `stdout`/`stderr` captured into the audit record | medium | accept | Command output may contain host detail; capturing it is the explicit purpose of criterion 4 and the record is local to `.infrabrain/`, which is gitignored |
</threat_model>
