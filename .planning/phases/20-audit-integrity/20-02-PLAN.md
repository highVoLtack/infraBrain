<objective>
Stop this phase from silently degrading replay.

Replay truncates at 20 events, newest-first. This phase roughly triples per-session step-event
volume. Left alone, the audit-integrity fix would push the OLDEST events — the early steps — out
of the replay window, making replay worse on sessions that render correctly today.

Purpose: implements locked decision D-5. `src/api/routes/history.ts` is a route handler, not a
renderer, and is explicitly in scope. `src/ui/App.tsx` and `src/cli/formatter.ts` stay hard-frozen.

Output: session-scoped queries return the whole session; global queries are unchanged.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client -> /history route | Untrusted query params (`limit`, `session`) cross here |
| route handler -> SQLite audit_log | Query construction crosses into the persistence layer |
| audit record -> auditor / pilot engineer | A truncated record reads as a complete one |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-04 | Repudiation | `/history` truncation at 20 events | high | mitigate | Session-scoped queries default to a limit that covers the whole session, so early steps cannot silently vanish from replay while the response still looks complete |
| T-20-05 | Denial of service | unbounded session query | low | accept | The default is a bounded constant (1000), not unbounded; a single session is bounded by one execution run, and the global query keeps its 20-row default |
| T-20-06 | Tampering | `limit` query param | low | accept | `parseInt` on an attacker-supplied limit is pre-existing behaviour and is passed as a bound SQLite parameter, not string-interpolated into SQL |
</threat_model>
