# Phase 12.3: Agnostic Skills + Engine-Proof Rewriter - Context

**Gathered:** 2026-03-14
**Status:** Ready for planning
**Source:** Live Permission Trap UAT + user feedback on skill hardcoding

<domain>
## Phase Boundary

Two problems revealed by live testing:

1. **Rewriter blind spot:** When LLM writes `docker exec permission-app chown ...`, the rewriter passes through unchanged — no `-u 0` injection. The chown fails as UID 1000.

2. **Skills are not agnostic:** All skills contain hardcoded container names (`permission-app`, `postgres-demo`, `storage-logger`) and docker exec commands in their prompts and examples. This means a skill only works for its specific demo scenario, not for any real-world instance of the same problem.

The user's vision: "Wozu nutzen wir LLMs wenn wir ihnen sagen müssen wie nginx läuft?" — Skills should describe the DOMAIN (filesystem permissions, postgres connections, disk usage), not the INFRASTRUCTURE (specific container names, docker commands).

</domain>

<decisions>
## Implementation Decisions

### Rewriter: Docker-Exec-Aware Parsing
- When command starts with `docker exec`, parse it: extract flags, container name, inner command
- Apply rewrite rules to the INNER command
- Reassemble with injected flags (e.g., `-u 0` for chown)
- Belt-and-suspenders: works even if LLM ignores COMMAND-ONLY instruction

### Skill Prompts: COMMAND-ONLY Mode for ALL Skills
- Every skill system prompt must say: "Write ONLY bare commands. The engine handles container targeting and privilege escalation. DO NOT write docker exec."
- Examples in skills must show bare commands, not docker exec wraps
- The postgres "SQL-ONLY" pattern is the gold standard — extend to all skills

### Discovery: Dynamic Container References
- Discovery commands in frontmatter that reference specific container names are a problem for agnosticism
- BUT: Discovery runs BEFORE diagnosis, and its purpose is to find out what's running
- Solution: Discovery commands that are generic (like `docker ps -a`) stay as-is
- Discovery commands that reference specific containers (like `docker logs permission-app`) need to be either:
  - Removed (the LLM should discover container names from `docker ps -a` output)
  - OR kept but understood as "default hints" that the engine resolves at runtime

### What Stays Specific
- Discovery commands for `docker ps -a` — these are generic
- Rewrite rules (match patterns, container: auto) — these are generic
- The ONLY specific thing should be the discovery frontmatter for known demo setups

### Claude's Discretion
- Whether to make discovery commands fully dynamic or keep demo-specific ones as defaults
- How to handle nginx skill (already writes full docker commands, different pattern)
- E2E test updates for canned fix plans that currently include docker exec

</decisions>

<specifics>
## Specific Ideas

- Skill prompt template for COMMAND-ONLY mode:
  ```
  ## COMMAND-ONLY MODE

  You write ONLY bare system commands. DO NOT write `docker exec`, `docker logs`, or any container management commands.
  The execution engine automatically:
  - Targets the correct container from Discovery ground truth
  - Escalates privileges when needed (e.g., chown runs as root)
  - Wraps commands for the execution environment

  Write the command as if you were logged into the system directly.
  ```

- For filesystem skill: `chown 1000:1000 /app/data` instead of `docker exec -u 0 permission-app chown 1000:1000 /app/data`
- For docker-storage: `truncate -s 0 /shared/app.log` instead of `docker exec storage-logger truncate -s 0 /shared/app.log`
- For postgres: Already correct (SQL-ONLY)
- For nginx: Needs assessment — nginx commands are `nginx -t`, `nginx -s reload` which are bare commands

</specifics>
