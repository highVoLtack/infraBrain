# Phase 12.3: Engine-Proof Rewriter - Research

**Researched:** 2026-03-14
**Domain:** Command rewriting, docker exec parsing, skill prompt patterns
**Confidence:** HIGH

## Summary

The dynamic rewriter (`src/execution/dynamic-rewriter.ts`) has a passthrough bug on line 98-101: any command starting with `docker exec` is returned unchanged to "prevent double-wrapping." This means when an LLM writes `docker exec permission-app chown -R 1000:0 /app/data` instead of bare `chown`, the rewriter never injects `-u 0`, causing the command to run as UID 1000 and fail with "Permission denied."

The fix is surgical: replace the blind passthrough with a docker-exec-aware parser that extracts the inner command, applies rewrite rules to it (matching, stripping, wrapping, privilege escalation), then reassembles the full `docker exec` command with any missing flags injected. The second prong is updating skill prompts to use "COMMAND-ONLY" mode (like postgres uses "SQL-ONLY") so the LLM writes bare commands by default -- belt-and-suspenders.

**Primary recommendation:** Modify `dynamicRewrite()` to parse docker exec commands, extract the inner command, apply rules to the inner command, and reassemble -- rather than passing through unchanged. Update linux-filesystem-troubleshoot.md and docker-storage.md with COMMAND-ONLY instructions.

### Docker Exec Parsing Strategy

The CONTEXT.md suggests this regex:
```
^docker\s+exec\s+(?<flags>(?:-\S+\s+)*?)(?<container>\S+)\s+(?<inner>.+)$
```

**Analysis and refinement needed:**

The tricky part is distinguishing flags from the container name. Docker exec flags come in these forms:
- `-it` (combined short flags, no value)
- `-u 0` (short flag with value)
- `-e VAR=val` (short flag with value)
- `-w /dir` (short flag with value)
- `--user 0` (long flag with value)
- `--env VAR=val` (long flag with value)
- `--privileged` (long flag, no value)

The container name is the first non-flag argument. A flag is any token starting with `-`.

**Recommended approach:** Iterative token parsing rather than a single regex. Walk tokens left-to-right:
1. Skip `docker` and `exec`
2. While token starts with `-`: consume as flag (plus next token as value if flag takes one)
3. Next token is container name
4. Everything after is inner command

However, this requires knowing which flags take values. A simpler heuristic that works for the known cases:

```typescript
function parseDockerExec(cmd: string): { flags: string[], container: string, inner: string } | null {
  const match = cmd.match(/^docker\s+exec\s+(.+)$/i);
  if (!match) return null;

  const rest = match[1];
  const tokens = rest.split(/\s+/);
  const flags: string[] = [];
  let i = 0;

  // Known docker exec flags that take a value
  const VALUE_FLAGS = new Set(['-u', '--user', '-e', '--env', '-w', '--workdir']);

  while (i < tokens.length && tokens[i].startsWith('-')) {
    const flag = tokens[i];
    if (VALUE_FLAGS.has(flag) && i + 1 < tokens.length) {
      flags.push(flag, tokens[i + 1]);
      i += 2;
    } else {
      flags.push(flag);
      i += 1;
    }
  }

  if (i >= tokens.length) return null; // No container found
  const container = tokens[i];
  const inner = tokens.slice(i + 1).join(' ');
  if (!inner) return null; // No inner command

  return { flags, container, inner };
}
```

**Confidence: HIGH** -- Docker exec flag format is well-defined and the cases we need to handle are limited (the LLM primarily writes `-it`, `-u N`, or no flags).

### Reassembly Logic

After applying rewrite rules to the inner command:

```typescript
// Reassemble

```

### Anti-Patterns to Avoid
- **Regex-only parsing for docker exec:** Greedy/non-greedy regex struggles with variable flag formats. Token-based parsing is more reliable.
- **Modifying the function signature:** `dynamicRewrite(command, rules, containers)` is called from debug.ts in 2 places. Keep the same signature.
- **Double user injection:** If the LLM already wrote `-u 0` and the rule also says `user: "0"`, do NOT inject a second `-u 0`. Check before injecting.
- **Breaking the bare-command path:** The new docker exec branch is ADDITIVE. The existing bare-command pipeline (lines 104-136) must remain unchanged.

## Common Pitfalls

### Pitfall 1: Container Name vs Flag Confusion
**What goes wrong:** A regex assumes the container name is always the token after `exec`, but flags like `-u 0` come between `exec` and the container name.
**Why it happens:** `docker exec -u 0 permission-app chown ...` -- the `-u 0` must be consumed as a flag pair before `permission-app` is recognized as the container.
**How to avoid:** Token-walk approach that consumes known flags with their values before identifying the container.
**Warning signs:** Tests passing for `docker exec container cmd` but failing for `docker exec -u 0 container cmd`.

### Pitfall 2: Double-Wrapping When Rule Has Wrapper
**What goes wrong:** If the inner command is `chown 1000:1000 /app/data` and the rule has no wrapper, the inner command is used directly. But if a rule has a wrapper (like the SQL wrapper `psql -U postgres -c "{cmd}"`), applying the wrapper to an inner command that was already inside a docker exec could produce nonsense.
**Why it happens:** The wrapper replaces `{cmd}` with the full inner command. For non-SQL cases (chown, chmod), rules typically have no wrapper.
**How to avoid:** The rewrite rules for linux-filesystem-troubleshoot have no wrapper -- they only have `user: "0"`. The wrapper logic from the existing pipeline handles this correctly. Just ensure the docker-exec-aware path feeds the inner command through the same rule pipeline.

### Pitfall 3: Existing Test Breakage
**What goes wrong:** Test on line 102-105 expects `docker exec mycontainer ls` to pass through unchanged. After the fix, this command would be PARSED and the inner command `ls` would be matched against rules.
**Why it happens:** The test was written when passthrough was the desired behavior.
**How to avoid:** This test MUST be updated. The new behavior when a docker exec command arrives: parse it, try to match the inner command against rules. If a rule matches, apply it. If no rule matches, pass through the original docker exec command unchanged (preserving existing behavior for unmatched commands).
**Important:** When rules are `[sqlRule]` and the inner command is `ls`, no rule matches -- so the passthrough still happens. The test passes as-is IF the fallback for "no rule matches inner command" is "return the original trimmed docker exec command."

### Pitfall 4: E2E Tests Use Pre-Built Fix Plans
**What goes wrong:** The permission-trap E2E test (`poc-permission-trap.test.ts`) uses a canned fix plan that already has correct `docker exec -u 0` commands. The rewriter is applied to the fix plan in debug.ts (lines 421-426 and 481-486). Since the canned plan already has docker exec, the new parser will be invoked.
**Why it happens:** The mock returns `docker exec -u 0 permission-app chown 1000:1000 /app/data` -- which already has `-u 0`. The parser should detect the existing `-u 0` flag and NOT double-inject.
**How to avoid:** The "don't inject if already present" check handles this. Test explicitly.

### Pitfall 5: Inner Command Matching After Wrapper Application
**What goes wrong:** If the LLM writes `docker exec pg-container psql -U postgres -c "SELECT 1"` and the postgres rewrite rules try to match the inner command `psql -U postgres -c "SELECT 1"`, the second rule (`^psql\b`) matches. The rule then strips `-h`/`--host` and wraps in docker exec. But the inner command is already correct -- it doesn't need the psql strip treatment.
**Why it happens:** The postgres skill's rules are designed for bare SQL or bare psql commands, not for pre-wrapped docker exec + psql.
**How to avoid:** This is actually fine -- the strip_flags will try to remove `-h`/`--host` (which aren't present, so no-op), and the command reassembles correctly. The key insight is that the rewriter doesn't double-wrap with `psql -U postgres -c "..."` because the wrapper is only on the SQL rule, not the psql rule. The psql rule has no wrapper, just strip_flags. So inner `psql -U postgres -c "SELECT 1"` matches psql rule, gets strip_flags applied (no-op), then gets reassembled into `docker exec pg-container psql -U postgres -c "SELECT 1"`. Correct.

### Core: parseDockerExec helper function

```typescript
// Source: Designed from docker exec documentation + project constraints
interface DockerExecParts {
  flags: string[];
  container: string;
  inner: string;
}

const DOCKER_EXEC_VALUE_FLAGS = new Set([
  '-u', '--user',
  '-e', '--env',
  '-w', '--workdir',
]);

function parseDockerExec(cmd: string): DockerExecParts | null {
  const match = cmd.match(/^docker\s+exec\s+(.+)$/i);
  if (!match) return null;

  const tokens = match[1].split(/\s+/);
  const flags: string[] = [];
  let i = 0;

  while (i < tokens.length && tokens[i].startsWith('-')) {
    const flag = tokens[i];
    if (DOCKER_EXEC_VALUE_FLAGS.has(flag) && i + 1 < tokens.length) {
      flags.push(flag, tokens[i + 1]);
      i += 2;
    } else {
      flags.push(flag); // -it, -i, -t, --privileged, etc.
      i += 1;
    }
  }

  if (i >= tokens.length) return null;
  const container = tokens[i];
  const inner = tokens.slice(i + 1).join(' ');
  if (!inner) return null;

  return { flags, container, inner };
}
```

### Core: Modified dynamicRewrite docker exec branch

```typescript
// Replace lines 98-101 in dynamic-rewriter.ts
// OLD: if (/^docker\s+exec\b/i.test(trimmed)) return trimmed;
// NEW:
if (/^docker\s+exec\b/i.test(trimmed)) {
  const parsed = parseDockerExec(trimmed);
  if (!parsed) return trimmed; // Unparseable docker exec -- pass through

  // Strip -it/-i/-t from existing flags (belt-and-suspenders)
  let cleanFlags = parsed.flags.filter(f => !['-it', '-ti', '-i', '-t'].includes(f));

  // Try to match inner command against rules
  for (const rule of rules) {
    const regex = new RegExp(rule.match, 'i');
    if (!regex.test(parsed.inner)) continue;

    // Apply strip_flags to inner command
    let processed = parsed.inner;
    if (rule.strip_flags?.length) {
      processed = stripFlags(processed, rule.strip_flags);
    }

    // Apply wrapper to inner command
    if (rule.wrapper) {
      processed = rule.wrapper.replace('{cmd}', processed);
    }

    // Inject -u if rule specifies user and not already present
    if (rule.user && !cleanFlags.includes('-u') && !cleanFlags.includes('--user')) {
      cleanFlags = ['-u', rule.user, ...cleanFlags];
    }

    const flagStr = cleanFlags.length > 0 ? ' ' + cleanFlags.join(' ') : '';
    return `docker exec${flagStr} ${parsed.container} ${processed}`;
  }

  // No rule matched inner command: return cleaned docker exec (stripped -it)
  const flagStr = cleanFlags.length > 0 ? ' ' + cleanFlags.join(' ') : '';
  return `docker exec${flagStr} ${parsed.container} ${parsed.inner}`;
}
```
