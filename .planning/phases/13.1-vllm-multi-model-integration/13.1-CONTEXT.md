# Phase 13.1: vLLM Multi-Model Integration - Context

**Gathered:** 2026-03-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the Ollama-specific `ai-sdk-ollama` provider with a unified OpenAI-compatible provider (`@ai-sdk/openai`) that works with both Ollama and vLLM via baseURL switching. Enable hybrid deployment: vLLM serves fast small models (triage/routing), Ollama handles heavy models with CPU offloading. Per-role baseURL routing allows mixing backends in a single config.

</domain>

<decisions>
## Implementation Decisions

### Provider Architecture
- **Unified OpenAI-compatible provider** — use `@ai-sdk/openai` (Vercel AI SDK) for ALL backends
- Drop `ai-sdk-ollama` dependency entirely — Ollama's `/v1/` endpoint is OpenAI-compatible
- Single `src/llm/openai-compat.ts` replaces `src/llm/ollama.ts`
- Same `ModelRegistry` interface — zero changes to callers (debug.ts, executor.ts, etc.)
- BaseURL is the only difference between Ollama and vLLM — no separate provider code

### Deployment Model (Hybrid Architecture)
- **vLLM serves small fast models only** (e.g. qwen3.5:9b for triage/routing)
- **Ollama handles heavy models** (e.g. qwen3.5:122b-a10b) with CPU offloading on single GPU
- This is NOT multi-LoRA — different base models cannot be LoRA adapters on each other
- Single vLLM instance per small model, single Ollama instance for heavy model
- Future: when multi-GPU available, vLLM can serve larger models too

### Config & Routing
- **Per-role baseURL** in modelMap — each role can point to a different backend
- Rename `ollamaBaseUrl` → `defaultBaseUrl` (provider-agnostic)
- `defaultBaseUrl` is the fallback for roles without explicit baseUrl
- **Backwards compatible**: if modelMap value is a string → use `defaultBaseUrl`. If object with `{ model, baseUrl }` → use role-specific baseUrl
- No `provider` field needed — the baseURL IS the provider

### Structured Output
- Use vLLM's `response_format: { type: "json_schema" }` for generateObject calls
- **Parse fallback**: if generateObject fails, retry with generateText + manual JSON.parse + Zod validation
- This handles Qwen3.5 thinking mode interference with structured output

### Claude's Discretion
- Exact timeout values for vLLM vs Ollama endpoints
- Health check implementation for dual-backend status
- Whether to add `/v1` suffix automatically or require it in config
- Error message formatting when a backend is unreachable

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ModelRegistry` interface (`src/llm/types.ts`): `get(role)`, `getDefault()`, `entries()` — drop-in target
- `LLMProvider` interface: `streamDiagnosis`, `generateCommand` — wraps registry
- `createProvider()` (`src/llm/provider.ts`): role-aware output limits, budget checks — unchanged
- `InfraBrainConfigSchema` (`src/config/types.ts`): Zod schema for config validation

### Established Patterns
- `createOllamaProvider()` → custom fetch with AbortController timeout → same pattern for OpenAI
- `createModelRegistry()` loops over 7 roles, creates model instance per role → same loop, different provider
- `generateObject` used in debug.ts for structured diagnosis (Zod schema)
- `generateText` used in planner, self-healer, corrections

### Integration Points
- `src/api/routes/debug.ts`: creates registry via `createModelRegistry(config.modelMap, config.ollamaBaseUrl)`
- `src/api/routes/execute.ts`: same pattern
- `src/api/routes/status.ts`: health check hits `ollamaBaseUrl/api/tags`
- `src/config/loader.ts`: reads `.infrabrain/config.json`
- `src/config/types.ts`: `ModelMapSchema` currently `Record<role, string>` — needs union type

</code_context>

<specifics>
## Specific Ideas

- "Enterprise-mäßig" — naming should be provider-agnostic, not Ollama-branded
- "Provider-agnostic using the OpenAI API standard" — the abstraction layer IS the OpenAI API, not a custom InfraBrain abstraction
- vLLM is the future enterprise target, Ollama is the current single-GPU workhorse
- User wants to switch between backends by changing only the baseURL in config

</specifics>

<deferred>
## Deferred Ideas

- Multi-LoRA serving on single base model — requires v1.3 with proper LoRA pipeline
- Model benchmarking framework per role — v1.3 scope
- Parallel inference pipeline (9B pre-processes while 122B reasons) — needs vLLM multi-model first
- Auto-detection of available backends (try vLLM, fallback Ollama) — nice-to-have, not MVP

</deferred>
