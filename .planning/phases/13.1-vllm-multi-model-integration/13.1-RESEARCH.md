# Phase 13.1: vLLM Multi-Model Integration - Research

**Researched:** 2026-03-17
**Domain:** LLM Provider Abstraction / OpenAI-Compatible API / vLLM Deployment
**Confidence:** HIGH

## Summary

This phase replaces the Ollama-specific `ai-sdk-ollama` provider with `@ai-sdk/openai-compatible` from Vercel's AI SDK, enabling a unified OpenAI-compatible provider that works with both Ollama (`/v1/` endpoint) and vLLM via baseURL switching. The existing `ModelRegistry` interface remains unchanged -- only the provider construction layer changes.

The hybrid deployment model (vLLM for small fast models, Ollama for heavy models with CPU offloading) is the correct architecture for single-GPU RunPod. vLLM does NOT support serving multiple different base models on a single GPU simultaneously -- each vLLM instance serves one model. This means the deployment will be: one vLLM process for the 9B triage model, one Ollama process for the 122B heavy model. Per-role baseURL routing in the config maps each role to the appropriate backend.

**Primary recommendation:** Use `@ai-sdk/openai-compatible` with `createOpenAICompatible()`, per-role baseURL in ModelMap, and `supportsStructuredOutputs: true` for generateObject compatibility. The provider swap is a ~50-line change in `src/llm/` with zero caller modifications.

## User Constraints (from CONTEXT.md)

### Locked Decisions
- **Unified OpenAI-compatible provider** -- use `@ai-sdk/openai-compatible` (or `@ai-sdk/openai`) for ALL backends
- Drop `ai-sdk-ollama` dependency entirely -- Ollama's `/v1/` endpoint is OpenAI-compatible
- Single `src/llm/openai-compat.ts` replaces `src/llm/ollama.ts`
- Same `ModelRegistry` interface -- zero changes to callers
- BaseURL is the only difference between Ollama and vLLM -- no separate provider code
- **vLLM serves small fast models only** (e.g. qwen3.5:9b for triage/routing)
- **Ollama handles heavy models** (e.g. qwen3.5:122b-a10b) with CPU offloading
- This is NOT multi-LoRA -- different base models cannot be LoRA adapters on each other
- **Per-role baseURL** in modelMap -- each role can point to a different backend
- Rename `ollamaBaseUrl` -> `defaultBaseUrl` (provider-agnostic)
- `defaultBaseUrl` is the fallback for roles without explicit baseUrl
- **Backwards compatible**: if modelMap value is a string -> use `defaultBaseUrl`. If object with `{ model, baseUrl }` -> use role-specific baseUrl
- No `provider` field needed -- the baseURL IS the provider
- Use vLLM's `response_format: { type: "json_schema" }` for generateObject calls
- **Parse fallback**: if generateObject fails, retry with generateText + manual JSON.parse + Zod validation

- Error message formatting when a backend is unreachable

### Pattern 1: Unified Provider with Per-Role BaseURL

**What:** Each role in the ModelMap can specify its own baseURL, enabling mixed backends.
**When to use:** Always -- this is the core architectural change.

```typescript
// Source: @ai-sdk/openai-compatible docs + CONTEXT.md decisions
import { createOpenAICompatible } from '@ai-sdk/openai-compatible';
import type { LanguageModel } from 'ai';

const LLM_TIMEOUT_MS = 600_000; // 10 min for heavy models

function createCompatProvider(baseURL: string) {
  return createOpenAICompatible({
    name: 'infrabrain',
    baseURL,
    // No apiKey needed for local vLLM/Ollama
    fetch: (url, init) => {
      const controller = new AbortController();
      const timeout = setTimeout(() => controller.abort(), LLM_TIMEOUT_MS);
      return fetch(url, {
        ...init,
        signal: controller.signal,
      }).finally(() => clearTimeout(timeout));
    },
    supportsStructuredOutputs: true,
  });
}
```

### Pattern 3: Registry Construction with Per-Role Routing

**What:** Registry resolves each role to its own provider+model combination.
**When to use:** `createModelRegistry()` replacement.

```typescript
export function createModelRegistry(
  modelMap: ModelMap,
  defaultBaseUrl: string
): ModelRegistry {
  const models = new Map<ModelRole, { model: LanguageModel; modelId: string }>();
  // Cache providers by baseURL to avoid creating duplicates
  const providerCache = new Map<string, ReturnType<typeof createCompatProvider>>();

  function getProvider(baseUrl: string) {
    if (!providerCache.has(baseUrl)) {
      providerCache.set(baseUrl, createCompatProvider(baseUrl));
    }
    return providerCache.get(baseUrl)!;
  }

  for (const role of ROLES) {
    const entry = modelMap[role];
    const { modelId, baseUrl } = typeof entry === 'string'
      ? { modelId: entry, baseUrl: defaultBaseUrl }
      : { modelId: entry.model, baseUrl: entry.baseUrl };

    const provider = getProvider(baseUrl);
    models.set(role, { model: provider(modelId), modelId });
  }
  // ... same return shape as current
}
```

### Pattern 4: Structured Output with Parse Fallback

**What:** Try `generateObject` first, fall back to `generateText` + manual parse on failure.
**When to use:** All `generateObject` call sites (debug.ts, planner.ts, router.ts).

```typescript
// The existing pattern in debug.ts already does this:
// 1. Try generateObject with Zod schema
// 2. Catch error -> fallback to generateText free-text
// This pattern is ALREADY IMPLEMENTED and needs no change.
// The @ai-sdk/openai-compatible provider with supportsStructuredOutputs: true
// sends response_format: { type: "json_schema" } which vLLM supports natively.
```

### Anti-Patterns to Avoid
- **Separate vLLM and Ollama provider files:** The whole point is ONE provider with different baseURLs. Do NOT create `src/llm/vllm.ts`.
- **Auto-appending `/v1` to baseURL:** Ollama's OpenAI-compat endpoint is at `/v1/` but the provider adds paths itself. Let the user configure the base (e.g., `http://localhost:11434/v1` for Ollama, `http://localhost:8000/v1` for vLLM).
- **Checking provider type at runtime:** No `if (isVllm)` branches. The abstraction is the OpenAI API -- both backends speak it.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| OpenAI-compatible HTTP client | Custom fetch wrapper to `/v1/chat/completions` | `@ai-sdk/openai-compatible` | Handles streaming, tool calls, structured output, retries |
| Structured output enforcement | Manual JSON extraction from free text | `generateObject` with `supportsStructuredOutputs: true` | vLLM's guided decoding constrains token generation |
| Provider timeout handling | Custom retry logic | Custom fetch with AbortController (existing pattern) | Already proven in current codebase |
| Health check protocol | Custom endpoint probing | OpenAI `/v1/models` endpoint | Both vLLM and Ollama implement this standard endpoint |

**Key insight:** The OpenAI API is the abstraction layer. Both vLLM and Ollama implement it. The AI SDK provider handles all the protocol details.

## Common Pitfalls

### Pitfall 1: Ollama /v1/ Endpoint Path
**What goes wrong:** Ollama's OpenAI-compatible endpoint is at `http://host:11434/v1/`, but the `@ai-sdk/openai-compatible` provider appends `/chat/completions` to the baseURL. If baseURL is `http://host:11434`, it becomes `http://host:11434/chat/completions` (wrong).
**Why it happens:** Ollama's native API is at `/api/`, its OpenAI compat layer is at `/v1/`.
**How to avoid:** Config must include `/v1` in the baseURL: `http://localhost:11434/v1`. Document this clearly.
**Warning signs:** 404 errors from Ollama.

### Pitfall 2: vLLM Model Name Mismatch
**What goes wrong:** vLLM uses the exact model path/name from `--served-model-name` or the HuggingFace path. Ollama uses short names like `qwen3.5:9b`.
**Why it happens:** Different naming conventions between backends.
**How to avoid:** The per-role config object includes the model name appropriate for each backend. vLLM role: `{ model: "Qwen/Qwen3.5-9B", baseUrl: "http://localhost:8000/v1" }`, Ollama role: `"qwen3.5:122b-a10b"` (string, uses defaultBaseUrl).
**Warning signs:** "Model not found" errors.

### Pitfall 3: generateObject Mode with Non-OpenAI Providers
**What goes wrong:** `generateObject` defaults to `tool` mode which requires tool-calling support. vLLM supports `json` mode (response_format) better than tool mode for structured output.
**Why it happens:** AI SDK defaults to tool-based structured output for OpenAI providers.
**How to avoid:** Set `supportsStructuredOutputs: true` on the provider AND potentially pass `mode: 'json'` to `generateObject` calls if tool mode fails. The `@ai-sdk/openai-compatible` provider respects this flag.
**Warning signs:** "Tool was not called" errors from generateObject.

### Pitfall 4: Qwen3.5 Thinking Mode Interference
**What goes wrong:** Qwen3.5 models with thinking mode enabled produce `<think>...</think>` blocks before JSON output, breaking structured parsing.
**Why it happens:** MoE models like Qwen3.5 have internal chain-of-thought that may appear in output.
**How to avoid:** vLLM's guided decoding (json_schema mode) constrains output at the token level, preventing thinking blocks from appearing. The fallback (generateText + manual parse) handles edge cases.
**Warning signs:** JSON parse errors with `<think>` prefix in raw output.

### Pitfall 5: Health Check Divergence
**What goes wrong:** Ollama's health endpoint is `/api/tags`, vLLM's is `/v1/models`. Current code hardcodes `/api/tags`.
**Why it happens:** Different API conventions.
**How to avoid:** Health check should try the OpenAI standard `/v1/models` endpoint (works for both when using `/v1` baseURL). For Ollama-only backwards compat, can try both.
**Warning signs:** Health check always shows "disconnected" for vLLM backend.

### Pitfall 6: Timeout Mismatch
**What goes wrong:** vLLM serves small models (9B) with <3s latency. Ollama serves 122B with 30-120s latency. A single timeout doesn't fit both.
**Why it happens:** Different model sizes on different backends.
**How to avoid:** Use per-provider timeout based on the provider's expected workload. vLLM timeout: 30s (fast models). Ollama timeout: 600s (heavy models). Could be per-role or per-baseURL.
**Warning signs:** Fast model calls waiting 600s on timeout for a failed connection.

### Health Check for Dual Backend
```typescript
// Source: OpenAI API standard -- /v1/models works on both vLLM and Ollama /v1/
async function checkBackendHealth(baseUrl: string): Promise<{ connected: boolean; models?: string[]; error?: string }> {
  try {
    const controller = new AbortController();
    const timeout = setTimeout(() => controller.abort(), 3000);
    const start = Date.now();
    const response = await fetch(`${baseUrl}/models`, { signal: controller.signal });
    clearTimeout(timeout);
    const data = await response.json() as { data: Array<{ id: string }> };
    return {
      connected: true,
      models: data.data?.map(m => m.id),
    };
  } catch (err) {
    return { connected: false, error: (err as Error).message };
  }
}
```

## Open Questions

1. **`/v1` suffix handling**
   - What we know: Ollama needs `/v1` in baseURL, vLLM typically serves at root or `/v1`
   - What's unclear: Should the config always include `/v1` or should code append it?
   - Recommendation: Require `/v1` in config -- explicit is better than implicit. Document clearly.

2. **Per-role timeout values**
   - What we know: vLLM (small models) is fast (<3s), Ollama (heavy models) is slow (30-120s)
   - What's unclear: Should timeouts be per-baseURL, per-role, or global?
   - Recommendation: Per-provider (baseURL) timeout. Fast backend: 30s. Heavy backend: 600s. Can be configured later if needed.

3. **Ollama backwards compatibility for health endpoint**
   - What we know: Current health check hits `/api/tags` (Ollama-specific). New approach should use `/v1/models`.
   - What's unclear: Should health check enumerate all unique baseURLs from config?
   - Recommendation: Health check iterates unique baseURLs from modelMap, calls `/models` on each. Single unified health response.
