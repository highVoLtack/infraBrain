# Phase 12.5: Intelligent Routing + Framework Merge - Research

**Researched:** 2026-03-14
**Domain:** Skill routing architecture, LLM-assisted selection, trigger-based pre-filtering
**Confidence:** HIGH

## Summary

Phase 12.5 fixes a critical routing bug: the current `selectSkill()` in `src/orchestrator/router.ts` sends only `{name, description}` to the LLM with a minimal system prompt. It completely ignores the `triggers` and `priority` fields already defined in skill frontmatter. This means `log-analysis` (with broad triggers like "error", "debug", "diagnose") would be selected for prompts that should route to domain experts like `linux-expert`.

The fix is a two-tier routing architecture: Level 0 deterministic pre-filter (substring match on triggers) prunes candidates before Level 1 LLM selection with an enriched prompt containing triggers, `when_not_to_use`, and priority. Two new frontmatter fields (`negative_triggers`, `when_not_to_use`) enable anti-hijack mechanisms. The existing `SkillFrontmatterSchema`, `SkillRegistry.list()`, `buildRoutingPrompt()`, and `selectSkill()` all need targeted modifications. The Sanity Checker needs DPEV sequence enforcement. The Permission Trap E2E test needs a scenario remix with dynamic container names.

**Primary recommendation:** Implement changes in three waves: (1) schema + registry enrichment + pre-filter logic, (2) routing prompt enrichment + Sanity Checker DPEV enforcement, (3) Permission Trap scenario remix + E2E test rewrite.

### Pattern 1: Level 0 Pre-Filter (New Function in router.ts)

**What:** Deterministic substring matching to prune skill candidates before LLM call
**When to use:** Always, as first step in selectSkill()
**Implementation location:** New function `preFilterSkills()` in `src/orchestrator/router.ts`

```typescript
// New enriched skill summary type
interface EnrichedSkillSummary {
  name: string;
  description: string;
  triggers: string[];
  when_not_to_use: string[];
  priority: number;
}

function preFilterSkills(
  skills: EnrichedSkillSummary[],
  userInput: string,
): EnrichedSkillSummary[] {
  const input = userInput.toLowerCase();

  // Step 1: Find skills with matching positive triggers
  const positiveMatches = skills.filter(skill =>
    skill.triggers.some(trigger => input.includes(trigger.toLowerCase()))
  );

  // Step 2: Exclude skills with matching negative triggers
  // (negative_triggers from frontmatter, read via registry.list())
  // Need access to full frontmatter for negative_triggers -- registry.listEnriched()
  // For now: negative_triggers handled separately

  // Step 3: If no positive matches, return ALL skills (LLM safety net)
  if (positiveMatches.length === 0) return skills;

  return positiveMatches;
}
```

### Pattern 2: Enriched Routing Prompt (Modified buildRoutingPrompt)

**What:** Include triggers, when_not_to_use, and priority in the routing prompt sent to LLM
**When to use:** Always, in Level 1 LLM selection
**Implementation location:** Modified `buildRoutingPrompt()` in `src/orchestrator/context.ts`

```typescript
// Enriched routing prompt with Negative Selection system message
const ROUTING_CONSTITUTION = `You are a skill router. Given a user query and available skills, select the most appropriate skill.

ROUTING PROTOCOL (Negative Selection):
1. First, EXCLUDE skills where the query matches any "When NOT to Use" reason
2. Among remaining candidates, prefer skills with matching triggers
3. Use priority as tie-breaker (higher = more specific domain expert)
4. If unsure, prefer domain experts (priority 10) over utility skills (priority < 10)

NEVER select a skill when the query clearly matches its "When NOT to Use" list.`;

export function buildRoutingPrompt(
  skills: EnrichedSkillSummary[],
  userInput: string,
): string {
  const skillList = encodeForLLM(skills, 'Available skills');
  return `User query: ${userInput}\n\n${skillList}`;
}
```

### Pattern 3: DPEV Sequence Enforcement (Extended Sanity Checker)

**What:** Validate that the DPEV execution sequence is followed in order
**When to use:** In the debug route handler, at each phase transition
**Implementation location:** New function in `src/api/routes/debug.ts` or extracted to `src/orchestrator/sanity.ts`

```typescript
type DPEVPhase = 'discovery' | 'diagnosis' | 'plan' | 'execution' | 'verification';

function enforceDPEVSequence(current: DPEVPhase, completed: DPEVPhase[]): void {
  const ORDER: DPEVPhase[] = ['discovery', 'diagnosis', 'plan', 'execution', 'verification'];
  const currentIdx = ORDER.indexOf(current);

  // Every preceding phase must be completed
  for (let i = 0; i < currentIdx; i++) {
    if (!completed.includes(ORDER[i])) {
      throw new Error(
        `DPEV VIOLATION: Cannot start "${current}" before "${ORDER[i]}" completes`
      );
    }
  }
}
```

### Anti-Patterns to Avoid

- **Coupling pre-filter to registry internals:** Pre-filter function should take enriched summaries as input, not reach into registry.skills Map directly
- **Hardcoding container names in E2E tests:** The entire point of the remix is to prove agnosticism -- extract names from discovery output
- **Putting negative_triggers in the LLM prompt:** negative_triggers are Level 0 only (deterministic exclusion). Only when_not_to_use goes to LLM.
- **Modifying selectSkill signature unnecessarily:** Keep the existing interface, change the internal behavior. Pre-filter happens inside selectSkill, not at the call site.

## Common Pitfalls

### Pitfall 1: Trigger Overlap Between Skills
**What goes wrong:** "error" appears in both linux-expert triggers AND log-analysis triggers, causing both to pass pre-filter
**Why it happens:** Broad triggers create false positives
**How to avoid:** Remove "error" from log-analysis (per CONTEXT.md decision), rely on negative_triggers to exclude log-analysis when domain expert matches
**Warning signs:** Pre-filter returns 4+ candidates consistently

### Pitfall 2: Empty Pre-Filter Results Causing Silent Fallthrough
**What goes wrong:** No triggers match, all skills sent to LLM, LLM picks randomly
**Why it happens:** Unusual/novel prompt phrasing that doesn't contain any trigger words
**How to avoid:** This is by design (LLM is safety net). Log when fallthrough occurs for monitoring.
**Warning signs:** N/A -- this is expected behavior

### Pitfall 3: Breaking Existing Tests with Schema Changes
**What goes wrong:** Adding required fields to SkillFrontmatterSchema breaks 506 existing tests
**Why it happens:** Test fixtures use makeSkill() without new fields
**How to avoid:** Use `.default([])` for negative_triggers and when_not_to_use, matching the pattern for discovery and rewrite_rules
**Warning signs:** Mass test failures after schema change

### Pitfall 4: Permission Trap Dockerfile Hardcodes /app/data
**What goes wrong:** Remix scenario needs /var/lib/internal/secrets but Dockerfile creates /app/data
**Why it happens:** Original demo Dockerfile has hardcoded paths
**How to avoid:** Parameterize DATA_DIR via ENV in Dockerfile and app.py. Read from os.environ.get('DATA_DIR', '/app/data')
**Warning signs:** Container starts but permission error references wrong path

### Pitfall 5: E2E Test Race Condition on Container Startup
**What goes wrong:** Test starts before container reaches broken state
**Why it happens:** Docker build + start takes variable time
**How to avoid:** Existing polling pattern (15 attempts, 2s apart) is proven. Keep it for remix scenario.
**Warning signs:** Flaky test on CI -- first assertion fails intermittently

### Pitfall 6: DPEV Enforcement Breaking Existing Flow
**What goes wrong:** Current debug.ts doesn't track phases explicitly, adding enforcement breaks working code
**Why it happens:** Retrofitting sequence tracking onto monolithic handler
**How to avoid:** Track phases with a simple completed[] array, check at each transition. Don't restructure the entire handler.
**Warning signs:** Existing E2E tests fail after DPEV enforcement added
