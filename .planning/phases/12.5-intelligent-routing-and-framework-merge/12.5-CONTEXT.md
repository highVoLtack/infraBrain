<decisions>
## Implementation Decisions

### Trigger Pre-Filter Logic (Level 0 Router)
- Substring matching as "Level 0" filter — high-performance, zero-cost gate to prune skill library before LLM-based "Level 1" router
- Case-insensitive: check if any trigger word appears as substring in user prompt
- When NO triggers match any skill: fall through to ALL skills (LLM is the safety net)
- Pre-filter reduces candidate set sent to LLM, preventing Context Rot
- New `negative_triggers` frontmatter field (array of strings): "Anti-Hijack" mechanism
  - If ANY negative trigger matches user prompt, skill is EXCLUDED from candidates even if positive triggers matched
  - Allows utility skills to explicitly yield to domain experts
  - Separate field from `triggers` — clean schema, clear semantics

### Routing Prompt Enrichment (Level 1 Router)
- Enriched routing prompt includes per skill: name, description, triggers, `when_not_to_use`
- New `when_not_to_use` frontmatter field (array of strings): explicit exclusion reasons
  - Exposed to LLM in routing prompt alongside triggers and description
  - Separate from `negative_triggers` (which are Level 0 pre-filter, never seen by LLM)
- Keep TOON-encoding for routing prompt (consistent with existing pattern, saves tokens)
- Enriched system message as "Constitution" for Skill Router:
  - Instructs LLM to actively look for reasons to EXCLUDE via "When NOT to Use" before including
  - "Negative Selection" process: exclude first, then select from remaining
  - Priority passed as hint (LLM sees it but makes final call)
- `registry.list()` must return enriched data: name, description, triggers, when_not_to_use, priority

### log-analysis Scope Narrowing
- REMOVE broad triggers: `error`, `debug`, `diagnose`, `why`
- KEEP log-specific triggers: `log`, `journal`, `syslog`, `docker logs`, `journalctl`, `logfile`
- Classification: "Tier 2 Specialist" (priority 9) — equal peer for log tasks, always yields to Tier 1 Domain Experts (priority 10) when infrastructure component identified
- Add `when_not_to_use` to log-analysis: explicit exclusions for infrastructure component queries
- Add `negative_triggers` to log-analysis: prevent matching on domain-expert territory

### Permission Trap Pass Criteria (Agnosticism Proof)
- **Scenario Remix**: Rename container from `permission-app` to `vault-processor-99`, change target directory from `/app/data` to `/var/lib/internal/secrets`
- **Dynamic E2E Test**: Test must NOT use hardcoded strings — fetch container name and path from Discovery output, just like the real engine
- **Failure Adaptation Rule**: If live test fails, slightly adjust failure scenario (change name, UID, or path) to ensure next run is based on fresh reasoning, not cached patterns
- **Dual-Layer Validation**:
  - Unit mock tests: validate routing logic (linux-expert selected, trigger pre-filter works, negative triggers exclude log-analysis)
  - Live Docker integration test: full DPEV chain with remixed scenario (vault-processor-99)
- **Full DPEV chain must pass**: routing → discovery → diagnosis → chown with -u 0 → app recovers

### Sanity Checker as Protocol Enforcer
- Expand Sanity Checker scope beyond hallucination checking to DPEV sequence enforcement:
  1. Discovery ran before diagnosis
  2. Diagnosis completed before fix plan
  3. Fix plan uses only discovered entities
  4. Verification runs after execution
- Kill process immediately if DPEV sequence violated — Engine as "Protocol Enforcer"

### Framework Integration Principles
- Every diagnostic task starts with /clear context to prevent Context Rot (GSD principle)
- Engine acts as pure Protocol Enforcer — if LLM deviates from DPEV sequence, Sanity Checker kills immediately
- Negative Selection in routing: exclude first, then select

### What Stays
- MANDATORY_EXECUTION_PROTOCOL (anti-hallucination)
- checkForHallucinations() sanity checker (extended, not replaced)
- GROUND TRUTH injection from discovery
- dynamicRewrite() — unchanged
- Entire execution pipeline (executor, circuit breaker, damage budget)
- Universal expert skills (linux-expert, postgres-expert, network-expert)
- Tool map format from Phase 12.4

<specifics>
## Specific Ideas

- User's two-tier routing architecture:
  - Level 0: Substring trigger match (deterministic, zero-cost) → prunes candidates
  - Level 1: LLM with enriched prompt (Negative Selection logic) → makes final choice
- "Anti-Hijack" mechanism via negative_triggers — utility skills explicitly yield to domain experts
- "Zero-Trust Routing": enriched system message as "Constitution" that forces LLM to look for exclusion reasons BEFORE inclusion
- "Tier 2 Specialist" classification for log-analysis (priority 9 vs domain expert priority 10)
- "Scenario Remix" as agnosticism proof — `vault-processor-99` + `/var/lib/internal/secrets` instead of demo defaults
- "Failure Adaptation Rule" — change scenario details on test failure to prevent pattern caching

</specifics>
