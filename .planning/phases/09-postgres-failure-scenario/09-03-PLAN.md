Create `tests/e2e/poc-postgres-connleak.test.ts` following the exact pattern of `poc-nginx-502.test.ts` but adapted for the Postgres scenario.

**Structure (follow poc-nginx-502.test.ts 1:1):**

1. **Mock orchestrator modules** (same vi.mock calls as nginx test -- router, planner, context)

2. **Imports** (same as nginx test: Express, createServer, initDatabase, WriteThrough, AuditLogger, SkillRegistry, classifyCommand, validateCommand, InfraBrainConfigSchema, selectSkill, generateFixPlan, LLMProvider, FixPlan)

3. **Canned fix plan** -- 3-step Postgres connection termination:
   - Step 1 (read): `docker exec postgres-demo psql -U postgres -t -c "SELECT pid FROM pg_stat_activity WHERE state='idle' AND usename='leaky'"` -- Identify leaked PIDs. Use `usename='leaky'` instead of IP address for robustness (per RESEARCH.md Open Question #3 recommendation).
   - Step 2 (write): `docker exec postgres-demo psql -U postgres -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state='idle' AND usename='leaky'"` -- Terminate all idle connections from leaky user. Risk: `write`.
   - Step 3 (read): `docker exec postgres-demo psql -U postgres -t -c "SELECT count(*) FROM pg_stat_activity"` -- Verify connection count recovered.
   - Summary: "Terminate leaked idle connections from leaky-app"
   - Complexity: "moderate"

4. **beforeAll:**
   - Run `bash demo/postgres/reset-postgres.sh` (cwd: PROJECT_ROOT, timeout: 120_000 -- longer than nginx because leaky-app needs time to saturate)
   - Verify broken state: poll `docker exec postgres-demo psql -U leaky -d postgres -c "SELECT 1"` until stderr contains "too many" (max 15 attempts, 2s sleep)
   - Create temp directory, session, SQLite, WriteThrough store (same pattern as nginx)
   - Create mock LLM provider where `generateCommand()` returns Postgres-specific diagnosis text:
     ```
     Diagnostic Ladder Investigation:

     Step 0 - Container Discovery: Found postgres-demo and leaky-app containers.
     Step 1 - Connection Saturation: 20/20 connections active. System is saturated.
     Step 2 - Idle Analysis: 18 idle connections from user 'leaky' (leaky-app container).
     Step 3 - Cross-Domain Correlation: leaky-app (172.20.0.3) holds 18 idle connections to postgres-demo. This is a connection leak.
     Step 4 - Fix Proposal: Terminate idle connections from leaky user.

     Root Cause: Connection leak from leaky-app -- 18 connections opened and never closed.
     Fix: Terminate idle connections via pg_terminate_backend.
     ```
   - Set up mocks: selectSkill returns postgres-troubleshoot skill, generateFixPlan returns cannedFixPlan
   - Create AuditLogger, config, Express app (same as nginx test)

5. **afterAll:**
   - `docker compose -f demo/postgres/docker-compose.yml down --remove-orphans` (best-effort)
   - Clean up temp directory

6. **Test cases:**

   **it('broken environment rejects new connections'):**
   - `docker exec postgres-demo psql -U leaky -d postgres -c "SELECT 1"` should fail with "too many connections" in stderr
   - Use try/catch on execSync -- the command should throw

   **it('diagnoses connection leak and generates fix plan'):**
   - POST /debug with prompt "Postgres is rejecting connections with too many connections error"
   - Assert: res.status === 200
   - Assert: res.body.diagnosis contains "leak" or "idle"
   - Assert: res.body.fixPlan defined with steps.length >= 2
   - Assert: res.body.skillMessage contains "postgres-troubleshoot"
   - Assert: res.body.sessionId defined
   - Store debugSessionId and debugFixPlan for next test

   **it('executes fix plan and verifies recovery'):**
   - POST /execute with { sessionId: debugSessionId, fixPlan: debugFixPlan, target: "postgres", adminName: "e2e-test" }
   - Assert: res.status === 200
   - Assert: res.body.status === "completed"
   - Assert: res.body.stepResults.length > 0
   - Verify recovery: `docker exec postgres-demo psql -U leaky -d postgres -c "SELECT 1"` should now succeed (no longer "too many connections")

   **it('audit trail contains full DPEV evidence'):**
   - Query audit log via store.queryAuditLog({ sessionId: testSessionId, limit: 100 })
   - Assert event types contain: skill_selection, decision, execution_start, step_complete, execution_complete
   - Assert at least one entry has reasoning with length > 0
