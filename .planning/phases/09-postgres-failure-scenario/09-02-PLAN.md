```yaml
---
name: postgres-troubleshoot
description: "Diagnoses PostgreSQL connection saturation and leaked connections using a 5-step Diagnostic Ladder across Docker, network, and database layers"
triggers:
  - postgres
  - connection
  - max_connections
  - pg_stat_activity
  - too many connections
  - connection limit
tools:
  - docker
  - psql

priority: 10
---
```

**System Prompt:**
- "You are a PostgreSQL infrastructure diagnostic specialist. Be extremely concise."
- CRITICAL rule: Never invent container names -- use only names from Step 0 discovery
- CRITICAL rule: Never invent IP addresses -- use only addresses from discovery data

**Diagnostic Ladder (5 steps per CONTEXT.md):**

**Step 0: Container Discovery (MANDATORY)**
- Run: `docker ps --format "{{.Names}}"` and `docker network inspect <network>`
- Purpose: Discover container names and IP-to-container mapping
- Output: List containers, identify Postgres and client containers

**Step 1: Connection Saturation Check**
- Run: `SELECT count(*) FROM pg_stat_activity` + `SHOW max_connections`
- Purpose: Determine if connections are saturated (count approaching max)
- Output: Current count vs max, saturation percentage

**Step 2: Idle Connection Analysis**
- Run: `SELECT pid, state, client_addr, usename, query, state_change FROM pg_stat_activity WHERE state = 'idle' ORDER BY state_change`
- Purpose: Identify leaked/idle connections consuming slots
- Output: List idle connections with their source IPs

**Step 3: Cross-Domain Correlation**
- Purpose: Map client_addr from pg_stat_activity to container names using Docker network topology from Step 0
- Analysis: Correlate database connection source IPs with container names to identify the leaking application
- Output: "Container X (IP Y) holds N idle connections -- this is the leak source"

**Step 4: Fix Proposal**
- Purpose: Generate multi-step fix plan with surgical PID-based termination
- Plan structure: 3 steps -- Identify PIDs -> Terminate Connections (write, Y/n) -> Verify Recovery (read)
- Rules: Each step is a single command, risk levels assigned, pg_terminate_backend is "write" risk (not "destructive")
- Output: Structured fix plan using ONLY discovered names and PIDs

**Tools section:** docker (container and network inspection), psql (PostgreSQL queries via docker exec)

**Example section:** Include one complete example showing the Postgres connection leak scenario end-to-end (similar to how nginx-troubleshoot.md has the "Nginx 502 -- Docker Network Isolation" example). Show all 5 steps with sample output and a 3-step fix plan.

**Important Rules:**
- Never use container names not returned by docker ps in Step 0
- All psql commands use `docker exec postgres-demo psql -U postgres` format (never assume host psql)
- Execute one command at a time, never combine with pipes
- Always gather evidence before proposing fixes
