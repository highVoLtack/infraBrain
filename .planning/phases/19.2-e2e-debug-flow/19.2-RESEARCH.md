# Phase 19.2: End-to-End Debug Flow - Research

**Researched:** 2026-04-15
**Domain:** Ink Terminal UI -- DPEV+E+V pipeline wiring, SSE event chaining, structured plan rendering
**Confidence:** HIGH

## Summary

Phase 19.2 completes the end-to-end debug flow in the Ink terminal UI. Currently, the `/stream/debug` SSE endpoint runs Discovery -> Diagnosis -> Plan and then marks the session "completed," even though execution and verification have never happened. The Ink UI shows "Session complete" after plan generation while the actual infrastructure problem (e.g., nginx 502) persists.

All the building blocks exist: `stream-execute.ts` has step-by-step SSE streaming with approval gates, `DPEVPanel.tsx` renders `StepCard` and `ApprovalWrite`/`ApprovalDestructive` components, and the `dpevReducer` handles `STEP_UPDATE`, `APPROVAL_REQUIRED`, and `APPROVAL_RESPONSE` actions. The work is wiring these together: (1) adding a discovery phase `active` event to the pipeline so the UI can show a spinner, (2) rendering the plan as structured steps with risk badges instead of raw markdown, (3) chaining plan approval to execution via the stream-execute SSE endpoint, (4) adding a verification phase after execution, and (5) only marking the session "completed" when the fix is verified.

**Primary recommendation:** Wire the existing components together rather than building new ones. The main gaps are: a missing discovery `active` SSE event in `pipeline.ts`, no plan-to-execution chaining in the Ink client, no structured plan rendering component, and premature session completion. Fix the timer bug in DPEVPhaseHeader for replay mode as a side fix.

### Architecture Decision: Single SSE Connection
The current architecture has TWO separate SSE endpoints: `/stream/debug` (DPEV pipeline) and `/stream/execute` (execution steps). Phase 19.2 should consolidate execution into the `/stream/debug` SSE connection to avoid requiring the Ink client to manage two concurrent SSE streams. This means:
- `stream-debug.ts` calls the executor internally after plan approval
- Execution events are relayed through the same SSE response object
- No second POST to `/stream/execute` needed from the Ink client

**Why:** The Ink client's `useSSE` hook manages a single connection. Opening a second connection mid-stream requires complex lifecycle management and risks race conditions. The simpler approach is to keep execution in the same SSE stream.

### Anti-Patterns to Avoid
- **Two SSE connections from client:** Do NOT have the Ink client open a second SSE to `/stream/execute`. Keep all events flowing through the single `/stream/debug` connection.
- **Raw Markdown plan display:** The `planTable` string from the pipeline uses chalk colors (not Ink). Do NOT render `planTable` in Ink -- use the structured `fixPlan` object directly.
- **Mutable reducer state:** The dpevReducer MUST remain pure. No side effects in the reducer.
- **Timer setInterval in replay mode:** DPEVPhaseHeader creates intervals for active phases, but replay sessions may have phases with `status: 'active'` that are actually historical. Must check if the phase is truly live vs replayed.

## Common Pitfalls

### Pitfall 1: React 19 Batched State Updates in Tests
**What goes wrong:** Tests using ink-testing-library check `lastFrame()` immediately after simulating input, but React 19 batches state updates.
**Why it happens:** React 19 automatically batches all state updates (including those triggered by useInput). The re-render happens asynchronously.
**How to avoid:** Use `setTimeout(50ms)` flush in tests before checking `lastFrame()`. This is a documented decision from Phase 19-03.
**Warning signs:** Tests pass individually but fail in batch, or `lastFrame()` shows stale content.

### Pitfall 2: DPEVPhaseHeader Timer in Replay Mode
**What goes wrong:** When replaying a session, phases with `status: 'complete'` but no `completedAt` (or `completedAt` computed from `startedAt + duration_ms`) cause the elapsed timer to tick forever.
**Why it happens:** DPEVPhaseHeader starts a setInterval for `status === 'active'` phases. In buildReplayState, a phase might temporarily be 'active' before its complete event is processed. Also, if completedAt calculation is wrong, `endTime - startedAt` grows unboundedly.
**How to avoid:** The timer should be conditional: only tick if the phase truly has no `completedAt` AND the session is in live mode (not replay). Add a `isReplay` prop or check `completedAt` presence before starting the interval.
**Warning signs:** Replay sessions show timers incrementing instead of fixed durations.

### Pitfall 3: Session Completion Race Condition
**What goes wrong:** Stream-debug marks session "completed" after runDPEV returns, but execution hasn't started. If the user exits before approving execution, the session appears "completed" but the fix was never applied.
**Why it happens:** Current code: `status: 'completed'` in persistState after try block succeeds.
**How to avoid:** Change the flow: after runDPEV, set status to `'plan-ready'` (not completed). Only set `'completed'` after execution succeeds. Set `'failed'` if execution fails. Only set `'completed'` if execution is skipped (user rejects plan).
**Warning signs:** Session panel shows "completed" sessions where the infrastructure issue persists.

### Pitfall 4: Execution Step Events from Two Sources
**What goes wrong:** The stream-execute route emits `exec:step` events with INITIAL pending status for all steps, THEN re-emits after execution completes. If the pipeline executor is called directly instead, step events may come in a different order.
**Why it happens:** stream-execute.ts emits pending events in a loop (lines 100-109), then emits results after `executePlan` returns (lines 161-172). The executor itself doesn't emit events.
**How to avoid:** When chaining execution from stream-debug, emit step events during execution using the executor's `requestApproval` callback to signal step transitions. Don't rely on stream-execute's pre/post emission pattern.
**Warning signs:** Steps appear as "pending" then jump to final status with no "running" intermediate state.

### Pitfall 5: Plan Approval vs Step Approval Confusion
**What goes wrong:** The approval flow has TWO tiers: (1) plan-level approval (approve the entire plan before any execution starts) and (2) step-level approval (approve individual write/destructive steps during execution). The UI must distinguish between these.
**Why it happens:** TERM-E02 requires plan-level approval. The executor's `requestApproval` callback handles step-level. Both use `status: 'awaiting-approval'` in the reducer.
**How to avoid:** Use different DPEVAction types: `PLAN_APPROVAL_REQUIRED` vs `APPROVAL_REQUIRED`. The plan approval shows all steps with risk badges; step approvals show individual commands.
**Warning signs:** User sees plan approval prompt for individual steps, or step approval for the entire plan.

## Open Questions

1. **Verification implementation**
   - What we know: SSEEventMap already supports `verification` as a phase name. Discovery commands are defined in the skill file.
   - What's unclear: Should verification re-run ALL discovery commands, or a subset? Should the LLM be involved in interpreting results?
   - Recommendation: Re-run the original discovery commands and compare key metrics. If the root cause indicator has changed (e.g., 502 -> 200, connection count dropped), mark as "fix verified." Keep it simple -- no LLM call for verification in v1.3.

2. **Plan rejection flow**
   - What we know: If the user rejects the plan (N at plan approval), the fix is not applied.
   - What's unclear: Should the session be marked "rejected" or "completed"? Should it fall through to manual?
   - Recommendation: Mark session as "completed" with outcome "plan_rejected". End the SSE stream cleanly. User can re-run with a different prompt.

3. **Execution step approval routing**
   - What we know: The executor's `requestApproval` callback needs to pause execution and wait for user input.
   - What's unclear: How to wire the executor's per-step approval to the SSE stream without stream-execute's separate connection.
   - Recommendation: Pass a `requestApproval` callback to `executePlan()` that emits `exec:approval` via the stream-debug SSE response and waits on a module-scoped Promise (same pattern as cache/plan approvals). Add a new POST endpoint `/stream/debug/step-approve` for individual step approvals.
