## Accomplishments

- **Plan approval UI wired:** When `state.status === 'plan-approval'` and `state.fixPlan` is populated, DPEVPanel renders PlanView (numbered steps with risk badges) followed by an ApprovalWrite prompt titled "Execute this plan?". User response dispatches through `onPlanApprovalResponse`.
- **Verification section rendered:** Whenever `state.verificationResult` is populated, a "Verification" section renders with either "Fix verified" (green checkmark) or "Fix failed ({executionStatus})" (red cross). Renders regardless of status -- true to the data-only action semantics from Plan 02.
- **LiveDPEVPanel plan approval wiring:** New `handlePlanApprovalResponse` callback POSTs to `${apiBaseUrl}/stream/debug/plan-approve` with `{ sessionId, approved }` and dispatches `APPROVAL_RESPONSE` locally on success. `planApprovalError` state surfaces HTTP failures.
- **Step approval endpoint migrated:** `handleApprovalResponse` now POSTs to `/stream/debug/step-approve` (not `/stream/execute/approve`) with `{ sessionId, stepIndex, approved }`. This completes Plan 01's single-SSE architecture at the client side.
- **DPEVPanelContent interface extended:** New required `onPlanApprovalResponse: (approved: boolean) => void` prop. Replay mode passes `() => {}`, live mode passes the real handler.
- **Integration test coverage:** 10 new panel tests covering all 8 plan-required behaviors + "no PlanView when status != plan-approval" + "verificationResult renders even in error state"; 2 new reducer edge cases for PLAN_APPROVAL_REQUIRED with empty fixPlan and VERIFICATION_RESULT when status is already 'error'.

## Decisions Made

- **ApprovalWrite reused for plan-level approval.** Instead of introducing a `PlanApprovalPrompt` component, wrapped the existing ApprovalWrite with `command="Execute this plan?"` and `riskLevel="write"`. Keeps the Y/N keyboard UX identical across plan-level and step-level approvals and avoids component proliferation.
- **Verification placed between execution and completion footer.** The pass/fail verdict is visually adjacent to the execution steps it verifies, and precedes the completion footer so the user sees the outcome before the session-complete marker.
- **Step approval body now includes sessionId.** Plan 01's `stepApprovals` map is keyed by `sessionId:stepIndex`, so the new POST body matches the server-side contract. Previous stream-execute route was keyed only by stepIndex (singleton session).
- **Separate planApprovalError state.** Errors from the plan approval POST are surfaced as a distinct Text node below the existing cache/approval errors. Makes debugging easier when multiple POSTs could fail in different lifecycle stages.
- **onPlanApprovalResponse required, not optional.** Explicit contract prevents accidental omission in future panel wrappers; replay mode provides an explicit no-op.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] Step approval POST body needs sessionId for Plan 01 backend**
- **Found during:** Task 1 GREEN implementation
- **Issue:** The plan's action text for migrating `handleApprovalResponse` to `/stream/debug/step-approve` specified `body: { sessionId, stepIndex, approved }`, but the current code only passes `{ stepIndex, approved }`. Plan 01's step-approve endpoint keys the stepApprovals Map on `sessionId:stepIndex`, so without `sessionId` the lookup would always fail and the user's Y/N response would never resume execution.
- **Fix:** Included `state.sessionId` in the POST body; added `state.sessionId` to the `useCallback` dependency array so the handler rebuilds when the session ID arrives.
- **Files modified:** `src/ui/panels/DPEVPanel.tsx`
- **Verification:** Existing panel tests still pass (replay mode doesn't drive the live endpoint); Plan 01 tests verify the endpoint contract and our body shape matches.
- **Committed in:** `fb107cd` (Task 1 GREEN)

**2. [Rule 2 - Missing Critical] planApprovalError surface**
- **Found during:** Task 1 GREEN implementation
- **Issue:** Plan's action text set up the handler but commented "// Plan approval error handling" without actually surfacing failures to the user. Silent failure on plan approval would leave the UI stuck in plan-approval forever.
- **Fix:** Added `planApprovalError` state and a Text node in the render tree alongside the other error surfaces.
- **Files modified:** `src/ui/panels/DPEVPanel.tsx`
- **Verification:** Matches the existing `cacheError` / `approvalError` pattern in the same file.
