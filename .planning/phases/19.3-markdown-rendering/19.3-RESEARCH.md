# Phase 19.3: Markdown Rendering in Ink - Research

**Researched:** 2026-04-17
**Domain:** Terminal Markdown rendering inside Ink v7 React component trees
**Confidence:** HIGH

---

## 1. Goal Recap

Phase 19.3 introduces a `MarkdownView` component (`src/ui/components/MarkdownView.tsx`) that
renders Markdown-ish strings — as they arrive from LLM diagnosis root-cause and fix-plan
narrative fields — with proper terminal styling: headings bold and colored, fenced code blocks
highlighted, inline code differentiated with a background tint, unordered and ordered lists
indented, bold and italic inline, and plain text unchanged. The component is used inside the
existing `DPEVPanel` center panel and in any replay view that shows diagnosis text, replacing
the current raw `StreamingText` passthrough that displays literal `## heading`, ` ```fence` ```
and `**bold**` tokens verbatim. It must integrate into the Ink `<Box>` tree — producing real
Ink `<Text>` and `<Box>` elements — so that Ink's Yoga flexbox layout, text measurement, and
line-wrapping machinery remain fully functional.

### ANSI String Handling in Ink v7 — Key Finding

**Finding:** Ink v7 `<Text>` children that are raw ANSI strings DO render correctly to the
terminal in most cases, but there is a layout subtlety that makes this approach fragile.
[VERIFIED: node_modules/ink@7.0.0 source, 2026-04-17]

The evidence chain from the installed source:

1. **`sanitize-ansi.js`** — Called inside `squashTextNodes()` before final output. It
   _preserves_ SGR sequences (`ESC[...m` — colors, bold) and OSC sequences (hyperlinks) but
   _strips_ cursor-movement and screen-control sequences. An ANSI string from `marked-terminal`
   (which uses only SGR color codes) passes through sanitize-ansi unchanged. This confirms
   marked-terminal ANSI strings are not destroyed by Ink's sanitization pass.

2. **`measure-text.js`** — Uses `widest-line` -> `string-width` -> `strip-ansi`. ANSI
   sequences are stripped before width measurement. Layout calculation is correct for ANSI
   children. [VERIFIED: node_modules chain]

3. **`wrap-text.js`** — Uses `wrap-ansi`. ANSI sequences are handled during line wrapping.
   Styled strings wrap correctly without breaking escape sequences mid-sequence.
   [VERIFIED: node_modules/ink@7.0.0/build/wrap-text.js]

4. **Double-wrapping risk:** If the Ink `<Text>` also has `bold`, `color`, or `dimColor`
   props set, chalk is applied _around_ the already-ANSI string in `Text.js`. This is safe
   — chalk handles nested ANSI by resetting and re-applying — but it produces larger output
   strings and makes test snapshots unpredictable because escape codes accumulate.

5. **Multi-line ANSI block limitation:** `marked-terminal` renders an entire heading as a
   single string including newlines (e.g. `"\n## Root cause\n\n"`). Wrapping this in a
   single `<Text>` node works for display but breaks Ink's per-line layout model: all
   lines in the string share one `ink-text` Yoga node, so cross-line relative sizing
   (e.g., a sibling `<Box>` that wants to align with line 2) is impossible.

**Verdict on ANSI approach:** Technically _renders_, but produces fragile snapshots,
prevents per-element sizing/layout control, and imports ~8.2 MB of new dependencies
dominated by `highlight.js` (5.4 MB). The ROADMAP.md phase 19.3 success criterion
explicitly caps the bundle addition at >150 KB as the threshold where the handwritten
option is preferred. 307 KB (micromark route) is above 150 KB, but 8.2 MB is far above
it. [CITED: .planning/ROADMAP.md line 207]

### marked-terminal peer dependency conflict with current marked@18

`marked-terminal@7.3.0` declares `peerDependencies: { marked: ">=1 <16" }`. The current
npm `marked` latest is `18.0.1` (released 2026-04-17). Installing `marked-terminal` requires
pinning `marked` to `15.x` (`15.0.12` is the latest within the constraint). This creates a
dependency split: the project would need `marked@15` as a direct production dependency even
though the project itself does not use `marked` anywhere. [VERIFIED: npm registry]

## 3. Recommendation

### Winner: Handwritten thin parser using `micromark` AST

**Rationale:**

1. **No ANSI boundary.** The renderer produces native Ink `<Box>` and `<Text>` nodes.
   Each heading, paragraph, list item, and code block is a separate Ink node with its
   own Yoga layout box. Per-element sizing, border, padding, and margin all work as
   expected. Snapshot tests capture clean terminal frames without ANSI escape bytes.

2. **Bundle impact is acceptable.** `micromark@4.0.2` (~210 KB) +
   `mdast-util-from-markdown@2.0.3` (~97 KB) = ~307 KB. This is the smallest viable
   parsing solution with a maintained, CommonMark-conformant AST. highlight.js (~5.4 MB)
   is explicitly not pulled in; code blocks receive a uniform `dimColor` + border without
   per-language syntax coloring in Phase 19.3 scope.

3. **Fully maintained.** `micromark` is the reference CommonMark tokenizer; it underlies
   remark, MDX, and the unified ecosystem. `mdast-util-from-markdown` is the standard
   micromark-to-MDAST bridge, both under active development (last releases early 2025/2026).
   [VERIFIED: npm registry]

4. **isTTY-agnostic by construction.** Because the renderer emits Ink `<Text>` nodes
   with explicit `bold`, `color`, and `dimColor` props, ink-testing-library's mock
   renderer (`isTTY: true` in its Stdin but a non-TTY Stdout) still exercises the
   component correctly. ANSI-based approaches would need chalk to have `level > 0`
   (chalk auto-disables on non-TTY — see Pitfall 6 below).

5. **Inline code differentiation without external libraries.** Using
   `<Text backgroundColor="gray" color="white">` achieves the inline-code visual
   distinction purely with Ink props.

6. **Replay mode idempotency.** The parser runs on the same string on every render
   (pure function: string -> AST -> JSX). Whether rendering live or from replay
   storage, identical input produces identical output deterministically.

**Fallback:** If the handwritten parser proves insufficient for a future phase
requirement (e.g., tables, definition lists, or interactive Markdown links), consider
`remark@15` with a custom `remark-ink` renderer plugin. `remark` uses the same
`mdast-util-from-markdown` AST; adding `remark` would cost ~additional 200-300 KB for
the processor runtime but reuse the AST understanding built in Phase 19.3.

**Do not use** `marked-terminal`, `ink-markdown`, or `@inkkit/ink-markdown` for this
phase. The first adds ~8.2 MB and produces ANSI strings incompatible with clean
snapshot testing; the latter two are unmaintained and incompatible with Ink 7 / React 19.

## 4. Implementation Sketch

```typescript
// src/ui/components/MarkdownView.tsx
import React from 'react';
import { Box, Text } from 'ink';
import { fromMarkdown } from 'mdast-util-from-markdown';
import type { Root, Content } from 'mdast';
import { theme } from '../theme.js';

export interface MarkdownViewProps {
  children: string;
}

// Heading colors mapped to depth (h1-h6)
const HEADING_COLORS = ['cyanBright', 'cyan', 'blueBright', 'blue', 'magenta', 'magentaBright'];

function renderNode(node: Content, key: string): React.ReactElement | null {
  switch (node.type) {
    case 'heading': {
      const color = HEADING_COLORS[(node.depth - 1) % HEADING_COLORS.length] ?? 'cyanBright';
      return (
        <Text key={key} bold color={color}>
          {node.children.map((c, i) => renderNode(c as Content, `${key}-${i}`))}
        </Text>
      );
    }
    case 'paragraph':
      return (
        <Box key={key} flexDirection="row" flexWrap="wrap" marginBottom={0}>
          {node.children.map((c, i) => renderNode(c as Content, `${key}-${i}`))}
        </Box>
      );
    case 'code':
      return (
        <Box key={key} flexDirection="column" marginY={1} paddingLeft={2}
             borderStyle="single" borderColor={theme.panelBorder}>
          {node.lang ? <Text dimColor>{node.lang}</Text> : null}
          <Text color="greenBright">{node.value}</Text>
        </Box>
      );
    case 'inlineCode':
      return <Text key={key} color="yellowBright" dimColor={false}>{`\`${node.value}\``}</Text>;
    case 'strong':
      return <Text key={key} bold>{node.children.map((c, i) => renderNode(c as Content, `${key}-${i}`))}</Text>;
    case 'emphasis':
      return <Text key={key} italic>{node.children.map((c, i) => renderNode(c as Content, `${key}-${i}`))}</Text>;
    case 'list':
      return (
        <Box key={key} flexDirection="column" marginLeft={2}>
          {node.children.map((item, i) => (
            <Box key={`${key}-item-${i}`} gap={1}>
              <Text>{node.ordered ? `${i + 1}.` : '-'}</Text>
              <Box flexDirection="column">
                {item.children.map((c, j) => renderNode(c as Content, `${key}-item-${i}-${j}`))}
              </Box>
            </Box>
          ))}
        </Box>
      );
    case 'text':
      return <Text key={key}>{node.value}</Text>;
    default:
      return null;
  }
}

export function MarkdownView({ children }: MarkdownViewProps): React.ReactElement {
  const ast: Root = fromMarkdown(children);
  return (
    <Box flexDirection="column">
      {ast.children.map((node, i) => renderNode(node, `md-${i}`))}
    </Box>
  );
}
```

**Integration in DPEVPanel** — replace `StreamingText` for diagnosis/plan narrative:

```tsx

```

## 5. Pitfalls

1. **Parsing on every render cycle.** `fromMarkdown(children)` is called on every
   React render. For a streaming diagnosis (hundreds of renders per second during token
   arrival), this re-parses the full accumulated string each time. Mitigation: memoize
   with `React.useMemo(() => fromMarkdown(children), [children])` so the AST is only
   re-computed when the string changes, not on unrelated parent re-renders.

2. **Incomplete Markdown at streaming boundaries.** While tokens are streaming in,
   the accumulated string is partial Markdown — e.g., a heading `## Ro` before the
   rest arrives, or an unclosed code fence ` ``` `. `micromark` and `mdast-util-from-markdown`
   are designed for complete documents. Partial input may produce an unexpected AST (the
   partial line becomes a paragraph, the fence never closes). The fix is **deferred
   rendering**: keep using `StreamingText` while the phase is actively streaming
   (`phase.status === 'active'`), then switch to `MarkdownView` once the phase completes
   (`phase.status === 'complete'`) and the full token string is settled. This is the
   cleanest UX pattern: live streaming looks like a typewriter, completed phases render
   styled. Alternatively, switch to `MarkdownView` after a 200 ms idle debounce.

3. **Code block width overflow.** Fenced code blocks often contain long lines (stack
   traces, command output, config diffs). Ink's `<Box borderStyle="single">` does not
   clip child text by default; long lines wrap at `<Text wrap="wrap">` width, which is
   the box width. Set `<Text wrap="truncate-end">` on code block lines, or add
   `overflowX="hidden"` (Ink v7 Yoga property) to the code Box. Alternatively, keep
   `wrap="wrap"` but add a max-width computed from `useWindowSize().columns - 6`.

4. **ANSI escape byte sequences in snapshot tests.** If any `<Text color>` or `bold`
   prop is present, `lastFrame()` from ink-testing-library contains ANSI escape sequences.
   Snapshot tests that assert on `toMatchSnapshot()` will diff on escape byte values,
   not on visible content. Mitigation: use `toContain()` assertions on visible text
   strings (heading text, bullet text, code content) rather than full-frame snapshots.
   For structural snapshots, use a helper `stripAnsi(lastFrame())` (strip-ansi is already
   a transitive dependency in node_modules) to normalize before asserting. See §6 below.

5. **Nested `<Text>` key collision.** The recursive `renderNode()` uses composite keys
   like `"md-0-1-2"`. If the same Markdown string is rendered in two sibling `MarkdownView`
   instances (e.g., live panel + replay panel visible simultaneously), React key collisions
   are scoped to the component tree and are not an issue. However, if `MarkdownView` is
   ever rendered inside a `<Static>` component (Ink's permanent-output mechanism), keys
   must be globally unique. Add a component-level `id` prop to the key prefix if needed.

6. **chalk auto-disabling on non-TTY (not applicable to the recommended approach, but
   relevant if ANSI route is chosen).** chalk v5 auto-detects `process.stdout.isTTY`.
   When `isTTY` is false (piped output, CI), chalk level drops to 0 and all color output
   is stripped. `ink-testing-library` sets `Stdin.isTTY = true` but its mock `Stdout` has
   no `isTTY` property, leaving `chalk.level` at 0 in tests. An ANSI-based renderer would
   render plain text in tests — snapshot tests would pass but not exercise any styling.
   The Ink-native component approach avoids this entirely: `<Text bold color="cyan">` is
   always in the component tree regardless of TTY state; the _rendered output_ may or may
   not contain ANSI depending on ink-testing-library internals, but the component logic is
   always exercised.

7. **Replay mode idempotency.** The DPEV replay path in `DPEVPanel` reconstructs a
   `DPEVState` from stored audit events. The `phase.tokens` string in replay is the same
   accumulated string stored during live execution. Because `MarkdownView` is a pure
   function of `children`, replay renders identically to live post-completion render.
   No special replay handling needed — this is a correctness benefit of the Ink-native
   approach.

8. **`fromMarkdown` module compatibility with ESM.** `mdast-util-from-markdown@2` and
   `micromark@4` are published as pure ESM packages (`"type": "module"` in their
   package.json). The InfraBrain project is also ESM (`"type": "module"`), so named imports
   work directly. No `createRequire` or dynamic `import()` workarounds needed.
   [VERIFIED: npm registry package.json fields]

9. **`listItem` children may be wrapped in `paragraph` nodes.** In CommonMark, a loose
   list (items separated by blank lines) wraps list item content in `paragraph` nodes.
   A tight list does not. The renderer must handle both: `listItem.children[0]` may be
   either a `paragraph` (with its own `children`) or a direct `text`/`inlineCode` node.
   The `renderNode` switch handles `paragraph` correctly so nested recursion resolves
   both cases automatically, but this is a subtlety to verify in tests with both tight
   and loose list fixtures.

## 6. Testability

### Existing test infrastructure

`tests/ui/components.test.tsx` uses `ink-testing-library@4.0.0` with the pattern:

```typescript
const { lastFrame } = render(React.createElement(MyComponent, props));
const frame = lastFrame() ?? '';
expect(frame).toContain('visible text string');
```

All existing component tests use `toContain()` assertions on visible text, not ANSI-aware
snapshot assertions. This is the correct pattern for `MarkdownView` tests.

### Snapshot strategy for MarkdownView

Do NOT use `toMatchSnapshot()` directly on `lastFrame()` because the frame contains ANSI
escape sequences that are brittle across chalk version updates and platform differences.

Use this pattern instead:

```typescript
// Structural presence assertions — preferred
expect(frame).toContain('Root cause');          // heading text visible
expect(frame).toContain('nginx.conf');          // code block content visible
expect(frame).not.toContain('##');              // Markdown tokens stripped
expect(frame).not.toContain('**');              // bold markers stripped
expect(frame).not.toContain('```');             // fence markers stripped

// If a full snapshot is needed, strip ANSI first
import stripAnsi from 'strip-ansi'; // already transitive dep
expect(stripAnsi(frame)).toMatchSnapshot();
```

`strip-ansi` is already in `node_modules` as a transitive dependency of `string-width`
(which is used by Ink). No new import needed.

## 7. Requirements Draft

The following requirements are proposed for `/gsd-discuss-phase` to refine. IDs follow the
`TERM-M0x` convention established in ROADMAP.md phase 19.3.

**TERM-M01 — Heading styling.**
Headings (`#`, `##`, `###`) in diagnosis output and fix plan narrative render bold and in a
color distinct from body text (proposed: `cyanBright` for h1, `cyan` for h2, `blueBright` for
h3). The raw `##` token is never visible in the terminal output.

**TERM-M02 — Code block presentation.**
Fenced code blocks render with a visible border and their content in a contrasting color
(proposed: `greenBright`). The opening ` ``` ` and closing ` ``` ` fence tokens are never
visible. An optional language tag (` ```typescript`) is shown as a dim label above the block.

**TERM-M03 — Inline code differentiation.**
Inline code (single-backtick) renders in `yellowBright` to visually distinguish it from
surrounding body text. The backtick characters are not shown.

**TERM-M04 — List indentation.**
Unordered list items (`-`, `*`, `+`) render with a `-` prefix and 2-space indentation.
Ordered list items render with `N.` prefix and 2-space indentation. Nested lists indent a
further 2 spaces per level.

**TERM-M05 — Plain-text passthrough.**
A string containing no Markdown tokens (no `#`, no ` ``` `, no `**`, no `-` list markers)
renders identically to the current `StreamingText` output — no visual difference, no added
spacing, no Markdown artifacts.

## 8. Out of Scope for Phase 19.3

The following items are explicitly excluded from Phase 19.3 to keep implementation and testing
tractable:

- **Syntax highlighting for code blocks.** No per-language token colorization (no
  highlight.js, no cli-highlight). Code block content renders in a uniform `greenBright`
  color. Language tags are shown as dim labels only.

- **Markdown tables.** The `table` MDAST node type is not implemented in `renderNode`.
  Tables are rendered as plain paragraph text (micromark parses them but the renderer
  ignores the node type and falls back to text content).

- **Interactive Markdown links.** The `link` node type (`[text](url)`) is not rendered
  as a clickable hyperlink (ink-link / OSC 8 sequences). Link text is rendered as plain
  body text; the URL is discarded.

- **Images.** The `image` node type is not rendered. Image alt text is rendered as plain text.

- **Horizontal rules (`---`).** Not rendered; rendered as an empty line.

- **Blockquotes.** The `blockquote` node type is not implemented. Content is rendered as
  indented plain text without the `>` prefix visual.

- **Nested bold-italic (`***`).** Nesting of `strong` inside `emphasis` (or vice versa)
  is parsed correctly by micromark but the renderer may collapse to bold-only or italic-only
  depending on which node is the outer wrapper. Full nesting support is deferred.

- **Streaming real-time Markdown rendering.** During active token streaming, `StreamingText`
  continues to handle display. `MarkdownView` is only applied to _completed_ phase text.
  Real-time Markdown parsing during streaming is out of scope.

- **Syntax-highlighted code blocks for exotic languages** (Rust, YAML, HCL, etc.) — no
  language-specific coloring at all in this phase.

`fromMarkdown` parser does not evaluate JavaScript. Security review is not required for

## 14. Open Questions

1. **When exactly to switch from StreamingText to MarkdownView during live streaming.**
   - What we know: parsing partial Markdown mid-stream produces messy output; completed phase
     text is well-formed Markdown.
   - What's unclear: whether a 200 ms idle debounce is sufficient, or whether the phase
     `status === 'complete'` transition event is the correct trigger.
   - Recommendation: gate on `phase.status === 'complete'`. The live experience shows
     raw text during streaming (acceptable — users see tokens arriving), then re-renders
     styled once the phase ends. This avoids all partial-parse issues.

2. **Heading color palette alignment with existing theme.**

   - What's unclear: whether using `cyanBright` for h1 conflicts visually with

   - Recommendation: define heading colors in `theme.ts` as `markdownH1`, `markdownH2`,
     `markdownCode`, `markdownInlineCode` constants — keeping them alongside existing theme
     values and allowing future adjustment without changing component code.
